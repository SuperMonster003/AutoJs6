# AutoJs6 无障碍自动化架构 (Accessibility Automation Architecture)

本文是无障碍 (a11y) 自动化体系的架构说明, 与 [accessibility-automation-roadmap.md](accessibility-automation-roadmap.md) 配套:
Roadmap 负责 "做什么, 做到哪了", 本文负责 "现在长什么样, 目标长什么样, 为什么".

维护约定:

1. "现状" 章节描述当前 `master` 的真实结构, 每个阶段 (P0-P6) 结束时更新, 以符号名 (类 / 方法) 而非行号为锚点.
2. "目标" 章节与 Roadmap 第 4 节保持一致; 若两者冲突, 以 Roadmap 的固定决策为准并回改本文.
3. "评估记录" 章节保存需要跨会话记忆的技术评估结论 (如 builder 代码生成方案), 避免重复评估.
4. 只用半角标点.

### 1.2 服务生命周期与状态

```
系统设置启用服务 ──> 进程内 onServiceConnected ──> 首个 onAccessibilityEvent
   (hasService)          (hasInstance / isRunning)        (isOperational)
   [Settings.Secure]     [registry: CONNECTED]            [registry: OPERATIONAL]
```

进程内状态 (P1.1 起) 由 `A11yServiceRegistry` 统一持有, 3 态: `UNBOUND` (无绑定实例) / `CONNECTED` (已绑定, 未收到事件) / `OPERATIONAL` (已收到事件). "系统设置中已启用" 不是进程内可观测的状态 (只能读 `Settings.Secure`), 因此不并入枚举, 仍由 `AccessibilityTool.hasService()` 提供; P1.2 的控制器负责把两者组合成失败原因.

迁移入口: `onServiceConnected -> registry.onConnected(this)` (置 `CONNECTED`, 重置操作态); `onAccessibilityEvent -> registry.onEvent(this)` (置 `OPERATIONAL`, 并在必要时采纳实例); `onUnbind / onDestroy / stop() -> disposeService -> registry.onDisposed(this)` (仅当它是当前绑定实例时置 `UNBOUND`). 状态监听者按 owner 注册: 抽屉状态事件 (`AccessibilityServiceStateChangedEvent`, 仅绑定关系变化时投递), 每个脚本运行时的 `auto.stateListener` (owner = 其 `AccessibilityBridge`, 脚本退出时注销), Node Bridge 的断开回调.

| 谓词 (`AccessibilityTool`) | 含义 | 数据来源 |
| --- | --- | --- |
| `hasService()` | 系统 `ENABLED_ACCESSIBILITY_SERVICES` 中包含本服务 | `Settings.Secure` |
| `hasInstance()` | 进程内存在服务实例 | `registry.isBound` |
| `isRunning()` | `hasService() && hasInstance()` | 组合 |
| `isMalfunctioning()` | `hasService() && !hasInstance()` (已启用但进程内无实例, 常见于进程被杀后) | 组合 |
| `isOperational()` | `isRunning()` 且已收到首个事件 | 组合 + `registry.isOperational` |

等待: `AccessibilityService.waitForStarted(timeout)` = `registry.await(CONNECTED, timeout)`, `waitForOperational(timeout)` = `registry.await(OPERATIONAL, timeout)`; 单一 `Condition`, 任何迁移都会 `signalAll`, 负超时无限等待, 中断时返回 `false` 并保留中断标志.

启停 (P1.2 起由 `A11yServiceController` 统一, `AccessibilityTool` 只是门面):

- `start(launchSettingsIfNeeded)`: 已运行直接返回 (不重启); 否则按顺序尝试 `ServiceStartStrategy` (Root: `settings put secure` 经 root shell, 值加单引号以允许空列表; SecureSettings: `Settings.Secure` 直写, 需 `WRITE_SECURE_SETTINGS`; Shizuku: 同样的 `settings` 命令经 Shizuku 用户服务执行, 需 Shizuku 运行且已授权, 排在最后因为经另一进程往返), 每个策略只改写 `enabled_accessibility_services` 列表 (不再写 `accessibility_enabled`, Android 7.0 起由系统自行维护), 结果以回读为准; 已列出但未绑定的服务先移出再写回以触发重新绑定; 策略均不可用或失败时按需打开系统设置页.
- `stop(launchSettingsIfNeeded)`: 策略 -> `disableSelf()` 兜底 (仅当回读已不在列表中才算成功) -> 按需设置页. 系统的解绑是异步的, `waitForStopped()` (注册表 `awaitUnbound`, 2000 ms) 等待它.
- `restart()`: `stop` -> 等待解绑 -> `start`; 不等待会被部分系统 (AVD API 26 实测) 合并为 "仍然启用". `auto(true)` 的强制重启走 `ensure(forceRestart = true)`, 同样等待解绑.
- `ensure(level, timeoutMillis, launchSettingsIfNeeded, forceRestart): EnsureResult`: 已满足直接返回; 已绑定只差首个事件时只等待; 否则策略 (每个给 2 s 完成绑定) -> 设置页, 然后等待 `level` 至 `timeoutMillis` (负数无限). 失败原因 `NOT_ENABLED` / `ENABLED_BUT_UNBOUND` / `BOUND_BUT_NOT_OPERATIONAL` = "设置中是否启用" x 注册表状态. `AccessibilityTool` 的 `ensureService()` / `ensureServiceOperational()` 失败抛带原因文案的 `ScriptException`, `startServiceAndWaitFor()` / `startServiceAndWaitForOperational()` (`auto.waitFor(timeout)`) 失败抛 `ScriptInterruptedException`.
- `restoreIfMalfunctioning()` (`AccessibilityServiceAutoStart`, 每个 `BaseActivity` 创建时): 只恢复 `isMalfunctioning()` 且等 2 s 后仍未绑定的服务, 不会重新启用用户显式关闭的服务.
- `awaitAvailable(timeoutMillis)` (P5.5, Flow `recoverService` 的安静恢复): 已绑定立即 true; 故障状态 (已启用但未绑定) 经 `ensure(CONNECTED, timeout, launchSettingsIfNeeded = false)` 由策略重新启用 (同 `restoreIfMalfunctioning` 的口径); 未启用的只 `registry.await(CONNECTED, timeout)` (D16: 尊重用户的有意关闭); 从不打开设置页. 经 `AccessibilityBridge.awaitServiceAvailable` 暴露给运行时.
- 策略写入串行化 (`writeLock`), 等待在锁外, 因此等待用户的脚本不会阻塞其它地方的停止请求.
- UI 触发点 (悬浮菜单的布局分析, 快捷设置磁贴, `AutoJs.kt` 的布局分析广播) 走 `AccessibilityTool.ensureServiceAsync(level, timeout, launchSettingsIfNeeded, onResult)`: `ensure` 在 `Schedulers.io()` 执行 (root shell 与等待绑定不阻塞主线程), 结果回主线程; 失败交给 `explainFailure(reason)` (未启用: 提示 + 设置页, 其它原因: 按原因 toast); 成功后立即接续自身功能 (`LayoutInspector.captureCurrentWindowWithRetry`, 10 x 300 ms, 服务刚绑定后活动窗口根节点可能短暂为 `null`), 因此服务未启用但可自动启动时一次触发即可.

已知平台问题: `onServiceConnected` 偶尔不回调但事件照常到达; 注册表的 `onEvent` 会直接采纳实例并置 `OPERATIONAL`, 等待方与状态监听者 (含 `auto.stateListener` 的 `onConnected`) 在这条路径上同样被唤醒 / 通知. P5.5 补全: 由事件采纳而未经 `onConnected` 的实例在 `Snapshot.adoptedByEvent` 上带标志 (迟到的 `onConnected` 与解绑清除, 操作态切换保留; `registry.adoptedByEvent`, `AccessibilityService.isAdoptedByEvent` / `isConnectedCallbackSeen`, `auto.state.adoptedByEvent`, 服务管理器诊断的进程内实例一行附注); `AccessibilityService` 在首个事件发现回调从未到来时调用一次 `onAdoptedWithoutConnectedCallback()` (记 `Log.w`), `AccessibilityServiceUsher` 在其中补做 `applyServiceInfoPreferences()` (稳定模式 / 手势观察写入 `serviceInfo`, 与 `onServiceConnected` 同一份代码), 使被采纳的实例与正常连接的实例行为一致. 复现工具 `build/smoke/p55-connect-probe.js` + `run-p55-connect.sh` (见 1.8); 2026-09-06 两机各 5 轮关闭 / 启用均走正常路径, 未复现.

默认 bridge: `AccessibilityService.bridge` 是伴生对象级的 `defaultBridge`, 由 `AbstractAutoJs.createRuntime()` 在创建每个脚本运行时时登记为最近一次创建的 bridge, 供无参 `UiSelector()` (脚本中的 `new UiSelector()`) 使用, 与服务实例的生死无关. `pickup` / `detect` 的 `Picker.Builder` 则直接绑定调用方 `scriptRuntime.accessibilityBridge`.

### 1.3 事件流

`AccessibilityService.onAccessibilityEvent(event)` 在服务主线程 (= 应用主线程) 串行执行 (P1.3 起):

1. `registry.onEvent(this)`: 首个事件把状态置为 `OPERATIONAL` (并在 `onServiceConnected` 未回调时采纳实例); 已是 `OPERATIONAL` 的同一实例不产生迁移. 实例计数 (`eventCount` 等) 更新.
2. `TYPE_WINDOW_STATE_CHANGED` / `TYPE_VIEW_FOCUSED` 时无条件更新 `fastRootInActiveWindow` (不再取决于是否有 delegate 关心, 且先于分发, 使 MODE_FAST 的回调已能看到新窗口).
3. `eventBus.hasSubscribers(type)` 为假则返回; 否则构造 `A11yEvent` 信封并 `eventBus.dispatch(它)`, 返回前 `seal()` (API < 33 框架随后回收原始事件).

`eventBus` (`A11yEventBus<A11yEvent>`, 伴生对象持有, 跨服务重启存活) 按优先级升序分发, 相同优先级按注册顺序, 处理器异常隔离并记录, 可消费订阅项返回 `true` 终止链:

| 优先级 | 订阅项 | 载荷 | 可消费 |
| --- | --- | --- | --- |
| `PRIORITY_OBSERVER` = -100 | 事件监视器等轻量观察者 (`addEventObserver(owner)`, 同 owner 替换) | `A11yEvent.record` (字段拷贝) | 否 |
| `PRIORITY_SCRIPT` = 0 | 脚本回调 (`auto.registerEvent`), 每个 (ownerId, 类型) 一槽, 重注册即替换 | `A11yEvent.wrapper` (每个事件至多构建一次) | 否 |
| 100 / 200 / 300 | `ActivityInfoProvider` / `AccessibilityNotificationObserver` / `AccessibilityActionRecorder` (`addDelegate(priority, delegate)`) | `A11yEvent.raw` + `service` | 是 |

订阅项选项 (`A11yEventBus.Options`): `distinctKey` + `distinctWithinMillis` (前沿去重: 键与上次投递相同且在窗口内则丢弃; 无键为纯节流, 无窗口则相同键持续丢弃), `debounceMillis` (后沿: 安静该时长后只投递这一串的最后一个; 投递物为 `A11yEvent.copied()` 即原始事件的拷贝, 在主 looper 上执行, 不能消费). `auto.registerEvent(name, callback, options?)` 的 `{ distinct, within, debounce }` 直接映射到它. 安静窗口检测: `eventBus.lastDispatchAtMillis`, `Subscription.lastMatchedAtMillis` (匹配类型即记录, 在去重之前), 供 P3 的 `waitForIdle` / `waitForEvent` 使用.

按键 (`onKeyEvent`) 走 `keyBus` (`A11yEventBus<KeyEvent>`, 类型 = keyCode), 同步分发: 观察者 (`OnKeyListener.Observer`, 优先级 0, 非消费; `events.observeKey()`, Node Bridge 输入观察) 先于拦截器 (`KeyInterceptor.Observer`, 100, 消费; `events.setKeyInterceptionEnabled`), 返回值即是否被拦截; 两个 `Observer` 类是总线上的兼容外壳 (方法名不变), 实例属性 `onKeyObserver` / `keyInterrupterObserver` 委托到伴生对象, 因此监听跨服务重启存活. 手势 (`onGesture`, 已弃用回调) 走 `gestureBus` (`A11yEventBus<Int>`), 目前无订阅者. 原 `eventExecutor` 已删除.

脚本退出时 `SimpleActionAutomator.removeAllEventsForThisRuntime()` = `eventBus.unsubscribeAll(ownerId)`, 只清理本脚本的回调.

### 1.4 查找与拾取

`text('登录').findOne(3000)` 的调用链:

```
UiSelector.findOne(timeout)        主线程禁止; = query(PollPolicy.within(timeout), 1).one()
  -> UiSelectorQuery.collection()  Poller 循环: 尝试 -> 次数 -> 超时 (尝试后测量, 严格超过) -> 可中断休眠 50 ms
    -> UiSelector.findWithin(1, timeout)   bridge.ensureServiceStarted(); 若 FLAG_FIND_ON_UI_THREAD: FutureTask 投递到 UI 线程, get(timeout) / 可中断 get()
      -> findImpl(roots, 1)        roots = bridge.windowRoots() (受 mode / flags / 窗口过滤器影响), 跳过黑名单包名
        -> searchAlgorithm.search(UiObject.createRoot(root), selector, max)   DFS (默认) 或 BFS, 泛型于 UiNode<N>, 结果为 ArrayList<UiObject>
```

- 轮询计划 `PollPolicy` (P2.4): `ONCE` 为 `find()` / `findOnce()` / `exists()` (单次尝试, 不休眠), `within(timeout)` 为 `findOne(timeout)` (0 或负数 = `FOREVER`), `FOREVER` 为 `untilFind()` / `untilFindOne()` / 弃用的 `findOne()` / `waitFor()` (以及经 `untilFind()` 的 `UiSelector.performAction`), 这些无上限的方法可能永久阻塞脚本线程, 停止脚本会中断其休眠或跨线程等待. `times` / `backoff` / `maxInterval` 目前没有脚本入口, 留给 P3 的 Flow 与 P4 的工具集. `FLAG_FIND_ON_UI_THREAD` 下每次尝试投递到 UI 线程的搜索以查询的 `timeout` 为预算 (而非剩余时间), 超时抛 `error_find_on_ui_thread_timeout` 并取消任务.
- `bridge.windowRoots()` = `WindowRootResolver.roots(policy)` (P1.4 起唯一实现): 有窗口过滤器时为通过过滤的 `windows[*].root` (与模式无关); 否则 `MODE_FAST` 取 `fastRootInActiveWindow`, `MODE_NORMAL` 取 `rootInActiveWindow`; 该根节点为 `null` 时按 `policy.fallback` 处理: 默认 `NONE` 返回空列表 (2026-09-05 起, 原先返回 `[null]`), `auto.setFlags(['appWindowsFallback'])` 时改为窗口列表中应用窗口的根节点 (焦点 > 活动 > 列表顺序). `auto.root` = `currentRoot(policy)` (有过滤器时首个通过过滤且有根节点的窗口, 惰性), `auto.rootInActiveWindow` = `activeRoot(policy)` (忽略过滤器). 三者都不应用黑名单.
- 黑名单 = 保护模式 (设置 > 脚本运行 > 保护模式, `Pref.isGuardModeEnabled`): `AccessibilityConfig` 构造时把自身包名加入黑名单并封印, 每个 bridge 一个实例 (脚本启动时读取, 运行中改设置不影响已启动的脚本). 开启后 AutoJs6 自身前置时 `find*` / `pickup` 一律为空, `SimpleActionAutomator.performAction` (`scrollDown()` 等节点动作) 直接返回 `false`; 全局动作 (`home()` / `back()`) 不受影响. 这是按设计的行为, 冒烟脚本以它为前置检查.

- `Selector` (`core/automator/filter/Selector.kt`) 是过滤器列表的 AND 组合; `UiSelector.append` 原地追加 (因此 `Selector.kt` 的全局函数每次都新建选择器, 见其 `@Caution` 注释).
- `pickup(root?, selector, compass?, resultType?, callback?)`: `selector` 可为字符串 / 正则 (content 匹配), `UiSelector`, 对象 (键 = 选择器属性名, 由 `SelectorMapParser` 按注册表解析: 值为数组时展开为参数并宽松转换 (字符串可作数字 / 布尔), `null` 取无参重载 (`action: null` 跳过), 函数只能用于 `filter`; 未知键或标量不合抛 `NoSuchProperty`, 数组不合抛 `IllegalValue`, `Picker.Builder` 把两者映射为原有的本地化错误), 数组 (组合); 找到后按 `compass` 导航, 按 `resultType` (`#` widget, `{}` collection, `[]` widgets, `$` content, `.` point, `@` selector, `?` existence, 各有别名与复数拼写; 其余字符串或 `[name, ...args]` 列表为按名称调用节点方法, 单元素列表的首项不是方法时回退到复数形式 (`['#']` = widgets); 别名表与分类在 `PickResultType`, 分派在 `Detector`, 反射调用在 `Invoker`) 转换.
- 选择器属性的唯一描述是 `SelectorRegistry` (P2.2): 每个属性 = 名称 + 重载列表 (参数名 / `SelectorArgType` / 取值范围) + 可选取值器 + 弃用目标; builder 方法 (`UiSelectorBuilders.kt`), 集合选择器解析与全局函数导出都由它派生, 字符串选择器语法 (P5.3) 与 `auto.explain` (P5.3) 也将以它为键名与取值来源. 数值参数: 全局函数, 集合选择器与 `detect` 的拦截器经 `JsArgumentCoercion` 统一按四舍五入转为整型; Rhino 直接调用 Java 方法 (`selector().depth(1.6)`) 仍按引擎规则截断.
- `detect(w, compass?, resultType?, callback?)` 是 `pickup` 的节点版.
- 集合的脚本形态 (P2.6 核实): 静态类型为 `UiObjectCollection` 的返回值 (`find()` / `untilFind()` / `children()` / `siblings()` / `UiObject.find(selector)` / `pickup` 的 `{}` 等) 经 `AndroidContextFactory.WrapFactory.wrap` -> `ScriptBridges.asArray` 变为真正的 JS 数组 (`Array.isArray` 为 true, `for...of` / `filter` / `map` / `forEach` / `some` / `every` / `indexOf` / `Array.from` 都是数组自身的), 数组上按名称绑定集合的全部公开方法 (每个名字带全部重载; 原先逐 `Method` 绑定只剩最后一个重载, P2.6 修复), Java 方法遮蔽同名的数组方法 (`slice` 即如此, 语义与 `Array.prototype.slice` 一致但返回仍带集合方法). 因此 Kotlin 侧不重复声明带回调的数组操作. `*Each` 动作返回 `BooleanArray`, 脚本侧是 `NativeJavaArray` (有 `length`, 可下标与 `for...of`). Rhino 对 Java 集合: `for...of` 可遍历 Java `List` (`NativeJavaList`), 不可遍历 Java `Iterator`.
- 罗盘 (compass) 语法由 `CompassParser` 定义: `p[p\d]*` (上溯, 多段求和), `c-?\d+([>c]?-?\d+)*` (逐级子节点, 负数从末尾计), `s[<>]?-?\d+` (兄弟: 绝对 / 相对), `k[k\d]*` (自身及至多 n 级祖先中首个可点击节点, 无则 `null`, D6). `%` 表示透传. 行走由 `Compass.navigate(start, compass | steps)` 在任意 `UiNode<N>` 上完成 (P2.1 起), `UiObject.compass()` 只补充本地化错误信息.
- 屏幕相关参数 (`bounds*`, 八个度量及其 `min` / `max` / 范围形式, `screenCenterX/Y`, `screenCoverage`) 在求值时经 `ScreenScale.Source.default` 解析 (P2.3 起; 设备边长按需读取, 旋转生效): `(-1, 1)` 为屏幕边长的比例, `-1` 为整条边, 其余为像素; `bounds*` 的 left / top 向下取整, right / bottom 向上取整并规范化, 度量按四舍五入. 字符串匹配规则集中在 `StringMatcher`: 普通字符串在 `equals` / `startsWith` / `endsWith` / `contains` 中字面比较 (`contains` 为子串; 6.7.0 Alpha13 至 D15 (2026-09-06) 之间曾编译为模式), 在 `matches` / `match` 中编译为模式 (JS 字面量形式 `"/re/i"` 保留标志); 正则参数在 `equals` / `matches` 中整体匹配, 在 `contains` / `match` 中任意位置匹配; 模式在 builder 调用时编译, 写错即报错.
- `UiNode<N : UiNode<N>>` (P2.1): 过滤器, 搜索算法与罗盘所面向的只读视图, 成员即 `UiObject` 面向脚本的方法 (`text()` / `desc()` / `content()` / `id()` / `idHex()` / `className()` / `packageName()`, 八个边界标量, 17 个布尔属性, 集合信息, `depth()` / `indexInParent()` / `childCount()` / `child(i)` / `parent()`, `actionNames()` / `hasAction()` / `performAction()`, `recycle()`); 自类型参数使 `parent()` / `child()` 保持调用方的静态类型. 不提供 Android-free 的边界值对象 (脚本可见的 `bounds()` 返回 `Rect`, 同名冲突).

`wait(cond, limit?, interval?, callback?)` (`Global.kt`): `cond` 为函数或 `pickup` 选择器; `limit < 100` 视为次数, 否则毫秒超时 (默认 10000); 间隔默认 200; `interval >= timeout` 时折叠为单次; 真值规则 `isWaitConditionSatisfied` (仅 nullish / `false` / `NaN` 不满足). 这些规则已抽为纯函数, 供 P3 的 Flow 复用.

Flow 核心 (`core/automator/flow/**`, P3.1): 链是 `FlowNode` 树 (步骤 `FlowStep` 为数据, 每个节点一次性结算为 `Fulfilled(value)` / `Rejected(error)`, 取消 = `Rejected(FlowError.Cancelled)`), `FlowScheduler.start(step, parent)` 创建并调度节点: 阻塞步骤 (`Wait` / `WaitStable` / `Sleep` / `Action` / `GlobalAction` / `Tool` (P4.2 的工具调用)) 在 worker `FlowLane`, 用户回调 (`Callback` 的 `then` / `catch` / `finally` / `map` / `filter` / `peek`) 在 script `FlowLane`, `run` 回调与自定义稳定比较器在 worker, 簿记步骤 (`Value` / `Scope` / `Timeout` / `Combinator` / `Retry`) 就地. 核心只经 `FlowBindings` 触及外界 (`probe` / `describe` / `invoke` / `isTruthy` / `perform` / `performGlobal` / `adopt`), 时钟与休眠注入; 可选的 `workerFactory` (P3.2 补) 让每条链的根得到自己的 worker lane (子节点共用根的 lane, 每个节点记录自己是否正在阻塞运行, 取消只中断该节点所在的 lane), 组合器为条件来源创建的等待也是根, 因此在运行时并发轮询 (与 `Poller` 相同, `Wait` 直接复用 `Poller`, 因此 `findOne` 的计时规则原样适用). 语义要点: 取值规则同 Roadmap 附录 A.4; 取消向下传播并向上停止没有其它存活续接的祖先, 中断 worker 上正在运行的阻塞步骤; `timeout(ms)` 是自执行时起的链截止 (截短之后的等待 / 休眠, 截止后的步骤以 `TIMEOUT` reason `chain` 拒绝); `retry` 只重跑紧邻的上一步骤; 稳定检测由 `Stabilizer` 状态机完成 (样本观察时即取键; `missing = FAIL` 在看到过之后的消失时以 `INVALID_TARGET` 拒绝; `waitForVisible` / `waitForHidden` 为其变体). 错误为密封类 `FlowError` (`code` / `step` / `selector` / `elapsed` / `attempts` / `reason`).

Flow 运行时接入 (`runtime/api/augment/flow/**`, P3.2): `FlowExecutor` 每个 `ScriptRuntime` 一个 (属性键 `flow.executor`, 注册到 `closeableManager`, 因此在 `onExit` 末尾关闭: 取消全部待定节点并停止工作线程); worker lane 由 `FlowWorkerPool` 提供: 每条链的根一条串行 lane (`workerFactory`), 任务在惰性缓存线程池的守护线程 `flow-<engineId>-<n>` 上按序运行 (空闲 10 s 消亡; 每次排空进入引擎的 Rhino Context; `interruptCurrent()` 只中断运行该 lane 当前任务的线程, 任务间清除中断标志), 因此独立的链与组合器的各来源并发阻塞 (单线程时 `flow.race(['A', 'B'])` 要等 A 超时才轮询 B, 与附录 A.6 的示例相悖), 同一根链的分叉仍串行; script lane 按创建链的脚本线程各一个 (`FlowScriptLane`, 经该线程 `Timer` 的 `setImmediate` 回投, 排空函数自身不抛出以免终止脚本), 每个脚本线程一个 `FlowScheduler` (以其 `Timer` 为键, 弱引用). 交给脚本的每条 Flow 在结算前持有创建线程的 `Loopers.waitWhenIdleToken` (无 Looper 的线程不持有), 未被 `sync` / `await` / `toPromise` 取走且没有续接的叶节点拒绝在控制台 warn (与 Promise polyfill 一致). 条件归一化 (`FlowCondition`): 字符串 / 正则 / `UiSelector` / 对象 / 数组 / 数字为选择器 (探测经 `UiSelector.pickup`, 结果类型默认 `widget`; nullish / `false` / `NaN` / 空串 / 空数组 / 空集合视为未找到), 函数为断言 (按同步 `wait` 的真值规则, 在 worker 上调用), `UiObject` 以 `refresh()` 探测, Flow 与 thenable 以其结算探测; 回调返回的 Flow / thenable 由 `adopt` 采纳 (thenable 对应 `FlowScheduler.defer` 创建的 `Adopted` 根节点, 由 `then` 的两个回调 `fulfill` / `reject`; 该根不可重跑, 且 `cancel` 经其所属调度器路由). 服务不可用时 `probe` / `perform` 抛 `A11yUnavailable` (`ensureServiceStarted()` 的 `ScriptException` 为 cause). 动作: 节点目标 (`UiObject` / 集合 / 节点数组, 集合为逐节点与) 映射到 `UiObject` 方法 (`appendText` = `setText(text() + s)`, `clear` = `setText("")`, `performAction(action, bundle?)`), 坐标目标 (`Point` / `[x, y]` / `{x, y}`) 的 `click` / `longClick` / `press` 走手势派发器, 全局动作走 `automator` 模块的实现 (`press` / `swipe` / `gesture` / `gestures` 复用其参数解析). 参数 (`FlowArguments`): `(cond, timeout?, interval?, onOk?, onErr?)` 或 `(cond, options, onOk?, onErr?)`, `*After` 形式再取两个数字为延迟; 选项 `timeout` (`Infinity` 不限, 0 单次) / `interval` / `times` / `stableFor` / `compare` / `missing` / `strict` / `delay` / `root` / `compass` / `resultType`; 默认值来自每脚本的 `FlowDefaults` (`flow.defaults({ timeout, interval, stableFor, strictActions, trace })` 经 `FlowArguments.applyDefaults` 写入, 未知键报错; ### 1.5 线程模型

| 线程 | 承担 | 约束 |
| --- | --- | --- |
| 脚本线程 (每个 `ScriptRuntime` 一个 Looper 线程) | 执行脚本, `wait` / `findOne` / `sleep` 在此阻塞; Flow 的用户回调 (`then` 等) 经 script lane 回投到创建链的脚本线程 (P3.2) | UI 模式脚本的主逻辑跑在主线程, 因此 `sleep` / `findOne` / `waitForActivity` 等有 UI 线程守卫 (`wait` 目前没有; Flow 的 `sync()` 有) |
| Android 主线程 | Activity / 悬浮窗 UI; `FLAG_FIND_ON_UI_THREAD` 时的查找 | `findWithin` 的跨线程等待为 `FutureTask` (P2.4 起): 有超时的查询以其超时为上限, 无上限查询可中断; UI 线程阻塞时 `findOne(timeout)` 抛可读错误而非挂起 |
| 无障碍服务主线程 | `onAccessibilityEvent` 与 JS 事件回调 | JS 回调在此同步执行, 回调越重, 事件积压越多 |
| `eventExecutor` (服务内单线程池) | 按键与手势观察者 | 服务销毁时 `shutdownNow` |
| servant Looper (`Loopers.servantLooper`) | `GlobalActionAutomator` 的手势派发与全局动作回调 | 首次使用时惰性初始化 |
| Timer / `setImmediate` | Promise polyfill 的 `then` 调度, `ScriptAsyncDispatcher` 的回投, Flow 的 script lane (`FlowScriptLane.post` -> `Timer.setImmediate`, P3.2) | Looper 退出后 `setImmediate` 抛出, 因此 lane 丢弃回调并记录警告; 脚本线程在 `Flow.sync()` 中阻塞时自行排空本线程的 lane (否则等待自己线程回调的链永不结算) |
| `flow-<engineId>-<n>` (每个 `ScriptRuntime` 一个缓存线程池, P3.2) | Flow 的阻塞步骤 (等待 / 稳定等待 / 休眠 / 动作), `run` 回调与自定义稳定比较器; 每条链的根一条串行 lane, 不同 lane 并发 | 惰性创建的守护线程, 空闲 10 s 消亡, 排空时进入引擎的 Rhino Context; 取消经 `Thread.interrupt()` 只中断运行该链当前任务的线程, 任务间清除中断标志; 不登记到 `threads` (否则阻止脚本退出), 脚本存活由每条 Flow 持有的 `waitWhenIdle` 令牌保证; `Flow.sync()` 在此类线程上禁止 (会死锁自己的链); 脚本退出时 `FlowExecutor.close()` 以 `shutdownNow` 停止 |
| `toolkit-<engineId>` (每个 `ScriptRuntime` 至多一条, P4.1) | 弹窗守护 (`PopupDismisser.watch`) 的各轮: 事件总线报告窗口变化 (去抖) 后在此线程上查找并点击候选项; 同步的工具调用不用它, 在调用线程上阻塞 | 首次使用时惰性创建的守护线程, 空闲 10 s 消亡, 任务在引擎的 Rhino Context 内运行; 同时只跑一轮 (正在跑时的变化被跳过); 守护的 `onDismissed` / `onError` 不在此线程调用, 而经 Flow 的脚本 lane 投回创建线程 (P4.2); 脚本退出时 `RuntimeToolkit.close()` 先停止守护 (释放等待令牌) 再以 `shutdownNow` 停止线程 |

### 1.6 节点生命周期

- 策略 (P1.5 起唯一出处): `NodeRecyclePolicy.forSdk(Build.VERSION.SDK_INT)`, API >= 33 为 `NO_OP` (`AccessibilityNodeInfo.recycle()` 本就是空操作, 现在连调用都省去), API < 33 为 `RECYCLE`. `NodeLifecycle.default` 是进程级实例; `release` 只在策略要求时执行回收, 抛出的异常 (节点已回收等) 记 `Log.w` 并吞掉, 不再打印堆栈也不中断查找.
- 回收点: DFS / BFS 对非命中且非根的节点 `lifecycle.release`, 命中上限后对已获取未遍历的节点也释放 (P0 加入, P1.5 改为经生命周期对象; `SearchAlgorithm.search` 的末位参数 `lifecycle` 供测试注入); `ScrollAction` / `ScrollMaxAction` / `UiObject.isShifted` 的探针 / `AccessibilityService.recycleFastRootInActiveWindow` / 诊断 (`A11yServiceDiagnostics`, `A11yServiceSelfCheck`) 同样经此. `UiObject.recycle()` 重写是回收本身 (有分配器时转 `allocator.recycle(this)`, 顺带从登记表移除).
- `AccessibilityNodeInfoAllocator`: 仍不接入生产路径 (`ScriptRuntime.selector()` 与 `auto.root` 等的 `allocator` 恒为 `null`), 但已是可用的参考实现: 以 `NodeLifecycle` 决定回收, 登记表 `NodeRegistry` 按对象同一性 (原 `HashMap` 按节点 id 相等去重, 指向同一视图的两个实例只回收其一), 无需回收的平台上不登记; compat 重载改在 `unwrap()` 后的原始节点上操作 (原先调用包装对象自身的访问器, 与 `UiObject` 的重写互相回调而无限递归, 这也是它此前无人使用的原因); `global` 已删除, `NONE` 保留 (不登记). 不接入的原因 (P1.5 评估, 见 KDoc): API < 33 节点按进程池化, 脚本自行回收过的实例可能已被其它脚本的 `obtain()` 复用, 退出时的批量回收会回收到别人的活节点 (API 24 模拟器实测); 不回收只是失去池化, 回收错误会跨脚本损坏状态.

使用指南 (据上表): `FLAG_FIND_ON_UI_THREAD` 只是把查找搬到主线程执行 (`UiSelector` 经 `bridge.post` 同步等待), 遍历本身的成本不变: AVD 上差异在噪声内, 平板上因主线程忙于界面 (悬浮窗渲染, HyperOS 桌面) 反而慢 2 ~ 8 倍, 且查找期间主线程不处理其它消息 (UI 模式脚本与悬浮窗会卡顿); 它存在的理由是历史兼容 (个别 ROM 上从非主线程调用 `getRootInActiveWindow` 返回空), 不是性能开关, 默认不要打开. `MODE_FAST` 以服务缓存的 `fastRootInActiveWindow` (最近一次 `WINDOW_STATE_CHANGED` / `VIEW_FOCUSED` 时取的根节点) 代替每次查询的 `rootInActiveWindow` 调用, 快 1.5 ~ 4.5 倍 (省的不只是取根节点的 1 ~ 2 ms IPC, 缓存根的子树也多由客户端缓存供给), 代价是根节点可能过期或属于另一个窗口: AVD API 24 上设置首页与悬浮窗的 `fast` 查询只见到 1 个节点 (缓存的是上一个事件时的根), 只有主界面正确, 平板上三块屏幕都正确; 因此只适合 '窗口切换事件之后立即大量查询' 且能用已知节点验证根是否正确的场景, 一般脚本保持 `normal`. 轮询 CPU: `findOne(timeout)` 的 50 ms 间隔在静态屏幕上每次尝试都做一次全树遍历, CPU 占用随树的大小与设备而变 (AVD 5 ~ 10%, 平板 30 ~ 37%); `eventAssistedPolling` 标志下休眠到无障碍事件到达为止, 降到 AVD 1.6 ~ 3.8%, 平板 10 ~ 15% (HyperOS 的桌面与设置持续产生事件, 因此不到零), 是长时间等待的首选 (P5.2). 惰性 `findIterator()` 全遍历与 `find()` 相当 (平板 1060 节点 16 ms), 其价值在提前停止而非全遍历. 数据 (2026-09-06, 每项 10 轮均值): AVD API 24 x86 上 65 / 115 / 302 节点的全树遍历 3 ~ 6 ms, 未命中 2 ~ 4 ms, `findOnUiThread` 无增益 (差异在噪声内), `fast` 快 2 ~ 4 倍但在设置首页与悬浮窗上取到过期的 1 节点根 (只有主界面正确); Xiaomi Pad 6 Pro API 35 上 104 / 1060 / 302 节点的全树遍历 4.6 ~ 18.4 ms, `findOnUiThread` 反而更慢 (设置首页 30.8 vs 18.4 ms, 悬浮窗 37.0 vs 4.6 ms: 主线程忙于界面时交接开销大), `fast` 快 1.5 ~ 4.5 倍且三块屏幕的根都正确; `windowRoots()` 本身 1 ~ 3 ms; 惰性 `findIterator()` 全遍历与 `find()` 相当 (1060 节点 16 ms); `findOne(2000)` 未命中的 50 ms 轮询占进程 CPU AVD 5 ~ 10%, 平板 30 ~ 37%, `eventAssistedPolling` 降到 1.6 ~ 3.8% 与 10 ~ 15% (HyperOS 的桌面与设置持续产生事件, 因此不到零). 首轮数据因 Rhino 把循环体内的 `const` 保持为首轮值而全部相同, 改用 `let` 后重跑.

## 3. 评估记录

### 3.1 builder 代码生成 (D9, 已决 2026-09-05, P2.2)

评估 (候选与维度见 Roadmap P2.2 第 3 条):

| 方案 | 构建时间 | IDE 索引与跳转 | `@Deprecated` / KDoc | 与 d.ts 生成的衔接 | 结论 |
| --- | --- | --- | --- | --- | --- |
| (a) KSP 处理器 | 每次构建多一个处理器轮次, 引入编译期插件与增量编译的不确定性 | 生成物在 `build/` 下, 跳转与评审落在非仓库文件 | 可表达, 但需要注解模型承载弃用目标与文档 | 需另产 `selector-signatures.json` | 否 |
| (b) Gradle 任务 + 模板 | 任务本身廉价, 但要维护触发条件; 生成物提交与否两难 (提交则任务与文件可能漂移而无人发现, 不提交则回到 (a) 的 IDE 问题) | 视生成物是否提交 | 由模板表达 | 同左 | 取其变体 |
| (c) 手写 + 一致性测试 | 零 | 最好 | 手写 | 手写 | 200 个手写方法正是 D9 要消除的 |

选择: (b) 的变体. 生成器 `SelectorBuilderGenerator` 放在测试源码集 (`app/src/test/.../core/automator/selector/`), 从 `SelectorRegistry` 渲染抽象基类 `core/accessibility/UiSelectorBuilders.kt` (每个重载一个方法, 一律 `= applyEntry(name, args...)`; `deprecatedFor` 渲染为 `@Deprecated(ReplaceWith)`, `range` 渲染为 `@FloatRange`), 生成物提交到仓库, `UiSelector` 继承它并只实现 `applyEntry`. 漂移由 `UiSelectorBuildersTest` 守住: 每次单元测试都重新渲染并与提交文件逐字比较, 不一致即失败并把新渲染写到 `app/build/generated-selector-builders/` 供复制; 另以反射核对每个注册表重载在 `UiSelector` 上恰有一个签名一致的 public 方法. 理由: 零构建成本, 零插件依赖; 生成物是普通源码 (IDE 索引 / 跳转 / diff / 评审全部可用); 漂移由测试而非 Gradle 任务保证; d.ts 签名 (P6) 可由同一注册表 / 同一生成器派生, 不再需要 `selector-signatures.json`. 代价: 修改注册表后需要手工复制一次生成物 (测试失败信息给出路径).

### 3.2 字符串选择器语法 (Q4 -> D13, 2026-09-05)

已决: 方案 B, 入口复用 `select`. 全局 `select('text=登录 clickable')` 返回 `UiSelector`; `UiSelector.select(String)` 追加解析出的过滤器; 无参 `select()` 保持 `ACTION_SELECT` 动作语义. 语法与约束见 Roadmap D13, 已于 P5.3 实现 (2026-09-06: `SelectorStringParser` + `UiSelector.select(String)`, 依赖 P2.2 的 `SelectorRegistry` 提供键名与别名; 实现细节见 1.4).

| 服务实例 (instance) | 进程内 `AccessibilityService` 对象, 由系统绑定后创建 |
| operational (可操作态) | 服务已收到首个事件, 可以正常查询与执行动作 |
| bridge | `AccessibilityBridge`, 每个脚本运行时一个, 持有模式 / 标志 / 窗口过滤器 (合为一个 `WindowRootPolicy`), 根节点获取委托 `WindowRootProvider` |
| 拾取 (pickup) | 以多种形态的选择器一次性完成 "查找 + 导航 + 结果转换" |
| 探测 (detect) | 对已有节点执行 "导航 + 结果转换" |
| 罗盘 (compass) | 描述相对导航的紧凑字符串 (`p` / `c` / `s` / `k`) |
| ownerId | 脚本运行时在事件回调盒中的标识, 用于按脚本注销 |
| Flow | P3 引入的 Promise 支撑的链式异步等待 / 动作对象 |
| toolkit | P4 引入的高阶组合动作 (智能点击, 滚动查找, 弹窗关闭等) |
