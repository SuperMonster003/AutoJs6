# 模型参与候选构造: 目标校正与原型设计

2026-10-07, 维护者明确原始期望为: 模型参与候选构造, 再从结果中推荐综合分最高的一个或多个方案.
这是对原 Roadmap D7 "模型只给既有候选排序" 的目标校正. 本文保留设计与验收要求; 首个离线构造原型已实现和训练, 但效果门槛尚未通过, 不代表可接入产品或发布.

本次保持 P0-P8 编号, 保留既有实现与历史验收记录. 原来的排序模型仍有价值, 但其测试、分发及效果记录不能替代构造模型的验收.

2026-10-07 实施记录: 87 维状态/动作特征、逐步构造与轨迹训练已在 JVM 测试/离线工具中完成, 并用真实采集的受控夹具及独立合成留出做三组对照. 59 棵树的 84,454 B 策略模型通过一致性与复现检查, 对照仍有集合覆盖退化, 故保留为冻结基线. 退化方案在语法中可合法重放, 诊断为具有有效后续的前缀被族内 beam 提前裁剪; 下一步从前缀保留/探索覆盖及跨构造阶段价值评估改进, 并复核终局排序. 本轮已查看的 test 不再用于调参后声称独立验收. 详见 [原型报告](../../tools/codegen-model/reports/construction-first-2026.10-1.md).

2026-10-08 实施记录: 第三轮只改训练数据, 语法、87 维特征、公平控制器、预算与终局排序器不变. 格式 2 导出为每个状态/动作同时记录观测均值与最佳后续 (观测到的完成价值上界的下界), 按单个/集合分别配额采样并交替两种控制器采集教师轨迹; 两种标签各训练一个策略 (144/159 棵树), 策略文件声明各自的分数语义, Kotlin 读取器接受两者, 搜索仍不跨步骤累加分数. 预注册准入要求验证集不劣于冻结第二轮策略, 结果首选 93.75% 对 94.64% 未通过, 新留出集未开启. 已查看回归集上的事后诊断表明两种标签都恢复了第二轮诊断出的 9 个集合覆盖损失, 最佳后续标签的候选质量上限超过固定启发式, 但冻结终局排序器在扩大后的候选集合上选出更差首选. 剩余差距集中在终局排序: 现有 tiny v1 排序器按原搜索器的候选分布训练, 需按规则与构造两种来源的候选重训/复核 (第 3 节末条), 并为大捕获确立构造时限. 详见 [第三轮报告](../../tools/codegen-model/reports/construction-third-2026.10-1.md).

## 1. 构造能力的边界

目标流水线:

```text
布局树 + 所选目标 + 结构化请求
    ├─ 规则构造分支 (基线与回退)
    └─ 模型参与的逐步构造分支
              ↓
    统一验证、精简、去重
              ↓
    对合格方案统一综合评分
              ↓
    输出首选及若干备选的经典 / Flow 代码
```

模型在完整定位计划尚未形成时介入, 依据当前布局、目标、计划前缀与合法后续动作, 选择锚点、属性条件、关系步骤、序号和结束时机.
规则负责限制合法动作及资源预算, 最终代码由既有渲染器输出. 属性值引用当前布局中实际存在的字段, 不自由生成 id、节点身份或 JavaScript 文本.
请求中的目标集合、动作、输入文本、查询方式与代码风格仍由用户决定, 模型不得修改这些要求.

只对 `CandidateSearch` 已返回的完整候选重新打分, 或更换一个名为 "生成器" 的排序接口, 不满足这次目标.
构造轨迹必须可以核对: 每一步的状态、合法动作、模型判断、实际选择以及最终形成的计划. 权重或策略变化应能影响构造轨迹和候选集合.
构造轨迹与候选集合变化共同证明模型参与了构造; 只改变最终展示集合不够, 也不自动证明质量更好. 质量与覆盖收益另行评估.

首个原型沿用 `LocatePlan` 已有五类形状. 其允许的关系和条件构成输出语法, 不要求每个新候选都来自原搜索器已经枚举好的完整计划.
当前 `Search` 与 `Up/Child` 不能任意混搭; 如果实验表明表达能力本身构成瓶颈, 才在 P0.4/P1.3-P1.5 中连同验证、渲染一起扩展, 不先引入未经支持的脚本 API.

## 2. 首选原型: 状态与下一动作的专用策略

优先验证小型数值模型对 `(构造状态, 一个合法后续动作)` 的评价, 由有界搜索器按这些判断逐步构造计划, 同时保留少量分支.
合法动作可以由程序枚举, 但不能预先生成完整答案后才让模型选择. 这是在构造过程中使用学习到的策略.

现有 `ObliviousTreeModel` 的数值向量到标量推理可作为复用起点. 新策略需要独立的特征定义、训练样本与权重; 不能把现有 64 维完整候选特征补零后用于未完成的计划.
小型神经结构解码器可作为原型不满足需求时的对照方向, 目前没有本项目实验证据据此锁定网络结构、参数量或设备性能.

训练目标和搜索分数必须对应. 按不同状态分别训练的排序原始分, 不能直接相加并宣称得到可比较的完整计划价值.
原型应验证同尺度的完成价值预测, 或明确归一化与长度处理的动作策略; 保存分数语义和搜索参数, 避免不受控地偏向短计划或分支数较少的状态.

模型引导程序搜索有已有研究路径, 例如 [DeepCoder](https://arxiv.org/abs/1611.01989) 和 [Neural-Guided Deductive Search](https://arxiv.org/abs/1804.01186).
这些研究支持本设计方向的可行性探索, 不是 AutoJs6 的效果、体积或性能验收证据, 本原型也不声称复现其算法.

## 3. 训练数据需要补充构造过程

现有布局采集、真值关联、多状态验证和任务划分可复用, 但完整候选的优劣标签不等于完整的构造训练集.

- 增加计划前缀、合法下一动作、后续完成情况、失败/死路和搜索成本. 中间特征仍由 Kotlin 的单一实现导出, 使用独立 schema/hash.
- 用更充分的离线搜索与受控探索收集轨迹; 不能只拆解原来最多 200 个候选而保留其全部搜索盲区.
- 用完成方案在后续状态中的正确定位情况评价轨迹. 未来快照、真值 key 与完成标签只能用于监督, 不进入推理特征.
- 补充模型自身策略访问到的状态, 不只学习理想示范前缀. 保持界面族/应用隔离的训练、验证、测试划分.
- 最终排序器用规则与模型构造的合格候选共同训练/复核, 检查候选分布变化后的适用性.

## 4. 综合评分与正确性

当前捕获布局上的请求一致性先作为硬门槛: 单目标命中所选控件, 集合与期望集合一致, 接收者/动作等约束满足.
失败方案不进入推荐, 即使模型分数很高也不例外. 验证仍受捕获窗口范围限制, 不保证未来界面或动作执行结果.

综合评分用于比较合格方案的预期稳定性、位置/动态内容依赖、结构复杂度等. 质量模型与确定性偏好的结合方式须在验证集上确定,
不能把生成动作置信度、完整候选的排序原始分和任意规则代价直接相加, 也不把最终分数显示为未经校准的成功概率.

在合格且去重后的本次结果中按同一终局标准取首选/前 K 个, 明确同分规则与候选来源. "最高分" 指本次预算内找到的方案, 不宣称穷尽所有可能定位程序后的全局最优.
排序步骤仍只能重排其合格输入; 模型开启与关闭时, 整条流水线的候选集合则允许不同.

## 5. 保留的基础与原条目内的补做范围

| 原条目 | 可复用的基础 | 尚需补做 |
| --- | --- | --- |
| P0.4, P1.2-P1.7 | 请求、定位计划、规则搜索、验证器、渲染器 | 受约束构造状态、模型候选来源、统一验证与合并; 必要时才扩展 IR |
| P2.4-P2.6 | 采集、后续状态真值、标签与划分工具 | 构造轨迹、失败状态、扩大离线探索、数据与标签来源记录 |
| P3.1-P3.6 | 数值特征导出、训练与评估基础 | 独立状态/动作特征与策略训练、终局排序复核、公平对照 |
| P4.1-P4.6 | 数值树解释器、包校验和一致性测试基础 | 构造组件/角色声明、特征与语法版本、读取/缓存适配、完整轨迹一致性与预算 |
| P5.2-P5.5, P6.1-P6.8 | 签名信任、下载、原子存储、导入、比较与管理界面 | 按构造/排序能力检查兼容性, 包/目录/登记摘要的相应演进与回归 |
| P7.1-P7.6 | 已计划的开关、下载交互、缓存、回退 | 接入构造与终局排序, 区分两阶段来源/回退, 旧排序包不得冒充构造模型 |
| P8.1-P8.5 | 效果门槛、设备矩阵、体积/性能与发布流程 | 构造贡献与候选质量上限评估、完整链路预算、端到端对照 |

目前包格式和登记逻辑限定 `kind=ranker`, 目录兼容性绑定现有候选特征 schema/hash; 新能力不能只换权重文件或显示名称.
需要明确区分旧排序包和带构造能力的模型包, 为组件、动作语法、特征版本和宿主要求提供可验证的元数据.
具体线格式在原型选型后落定, 已签名发布的测试 Release v1/v2 文件保持原字节, 不以覆盖既有版本的方式升级格式. 两个 Release 均使用既有排序包格式, 不代表已经有构造包格式 v2.

保持模型外置、不上传布局、无需通用预训练大模型的方向. 模型包总大小 < 100 MiB、APK 增量、32 MiB 常驻及 D19 时延仍是约束/验收目标, 不用理论参数量代替实测.
构造还需要限制活跃前缀、动作评分次数、深度和临时缓存; 2,000 次候选验证 (含精简后的重验) / 两分支合计 200 个保留候选本身不足以约束构造开销.
所有阶段与回退共享本次请求的计数和时限, 不得在失败后重置预算. 给规则分支以及最终排序/渲染预留预算, 复用已经验证的规则结果; 关闭模型时保持现有完整规则流程.
P95 <= 1 s 是统计验收目标, 不等同于每次请求硬截止; 原型须另行确定并验证硬截止. 预算耗尽且无合格方案时明确返回失败, 不承诺必有规则结果, 不把未完成前缀作为候选输出.
用户取消生成直接终止请求, 不自动回退. 只取消下载时停止传输并等待用户选择规则生成、重试或关闭, 沿用 D4 的交互意图.

## 6. 在接入 P7 前验证贡献

先在私有输出目录做可复现的端到端构造原型, 使用现有数据和专门覆盖搜索预算瓶颈的受控布局. 至少比较:

1. 冻结当前 CandidateSearch 的原规则搜索;
2. 新构造器使用固定启发式, 不使用学习到的策略;
3. 同一构造器使用训练后的模型策略.

三组使用相同请求、验证器、LocatePlan 表达规范、同一份终局排序器权重、精简/去重规则与总预算, 另与完整规则基线比较实际推荐效果.
原 CandidateSearch 不为实验而扩展, 如实记录各组实际覆盖的搜索空间; 新构造器的启发式与模型两组严格共用合法动作、搜索参数与预算, 只替换决策策略.
这样区分扩大搜索空间、修改搜索代码和模型判断各自的贡献. 不给模型分支更多验证次数或更长时限来制造提升, 不分别重训终局排序器来掩盖构造贡献.
参数只用训练/验证集确定; 留出任务不得回流训练或调参.

记录有效覆盖率、规范化后的新增候选、候选中最高 survival、最终 top1/top3 质量、逐任务退化、操作评分次数、峰值内存和各阶段 P50/P95.
条件排列不同不算新增方案; 也不能把所有当前命中同一目标的不同定位策略都合并成一个. 候选质量上限高于基线对应任务的所有候选, 才能证明突破该任务的基线质量上限.
所有预定留出任务进入覆盖率和端到端质量的分母, 零候选/失败不能剔除, 零候选的端到端质量按 0 计. 跨构造器比较 regret/top3Recall 时使用共同参考集合 (例如三组候选并集) 的 best(g); 不使用各自集合的不同最优值作横向优劣证明.

构造轨迹证明参与方式; 独立留出任务上的上述对照决定它是否有实际价值. 现有排序模型的指标以及 real-test=0 的数据都不能直接证明新构造能力有效.
原型未表现出收益时记录失败并改进特征、训练/搜索策略或模型结构, 不把 "换了候选来源名称" 当成达标, 也不先完成仅排序的 P7 接入来替代此目标.
