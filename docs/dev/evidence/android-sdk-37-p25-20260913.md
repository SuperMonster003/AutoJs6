## 规则与调用点

VERIFIED: 发送方通过 `setPendingIntentBackgroundActivityStartMode` 贡献自身的启动资格, 创建方通过 `setPendingIntentCreatorBackgroundActivityStartMode` 授权使用创建方的资格. Opt-in 本身不是无条件后台启动权限. Android 17 将发送方规则覆盖到 `IntentSender.sendIntent`; `ActivityResultLauncher<IntentSenderRequest>` 同样需要检查其实际 options 路径. [Activity security](https://developer.android.com/guide/components/activities/secure-bal).

VERIFIED: `ALLOW_IF_VISIBLE` 与 `ALLOW_ALWAYS` 均在 API 36 加入. Android 14 / 15 的分支必须使用它们支持的 `ALLOWED`; 不能仅因 compileSdk 37 就把新常量用于所有设备. [ActivityOptions](https://developer.android.com/reference/android/app/ActivityOptions#MODE_BACKGROUND_ACTIVITY_START_ALLOW_IF_VISIBLE).

SOURCE: 本机 `androidx.activity:activity:1.12.2` 的 `ComponentActivity` 先取 `options.toBundle()`, 再通过 `ActivityCompat.startIntentSenderForResult` 传给平台. `ActivityOptionsCompat.makeBasic()` 的返回 Bundle 不允许调用方修改; 宿主使用小型 `ActivityOptionsCompat` 适配器重写 `toBundle()`, 返回实际平台 options.

| 创建 / 发送位置 | token 目标与实际发送方 | 处理 |
| --- | --- | --- |
| `DrawerFragment` / `ScreenColorPickerTool` | 插件创建不可变 Activity token; 宿主发送; `PickerRequestActivity` 进入用户确认流程 | 添加发送方 options: API 36+ 为 `ALLOW_IF_VISIBLE`, API 34 / 35 为 `ALLOWED`, 更旧系统不传 options |
| `AndroidPackageSessionInstaller` | 宿主创建可变 Activity token, 明确限定 `PackageInstallStatusActivity` 与 session; `PackageInstaller.Session.commit` 交给系统发送 | 保留创建方 API 36+ `ALLOW_ALWAYS` / API 34 / 35 `ALLOWED`, 保留界面离开后的确认回调需求; 不改成发送方 setter |
| `ShortcutUtils` | 不可变 broadcast token; 系统 / Launcher 在固定成功后发送 | 成功回调没有启动 Activity 的代码, 不追加 Activity BAL 授权 |
| `external/shortcut/ShortcutManager` | 同上, `getBroadcast` 的固定成功回调 | 同上; 用户后来点击快捷方式属于独立的 Launcher 启动入口 |
| `ScriptWidget` | 不可变 Activity token; 用户点击小组件后由 Launcher 发送 | 保留点击入口, 不添加后台自动发送 |
| `NotificationUtils`, `ForegroundServiceUtils`, `PythonLongRunningForegroundService` | 不可变通知内容 Activity token; System UI 响应用户点击 | 保留用户点击路径, 不把通知显示等同于宿主已有 BAL 权限 |
| `PythonLongRunningForegroundService`, `NodeAudioRecorder` | `getService` 的停止动作 token | 不属于 Activity token |
| `IntentUtils.App.scheduleRestartAlarm` | 不可变 Activity token; AlarmManager 发送重启请求 | 单独记录, 不把闹钟 FGS / 音频规则与 Activity 启动规则合并 |
| `TimedTask`, `AlarmTimedTaskScheduler` | 不可变 broadcast token; 调度系统发送 | 广播触发脚本后, 脚本的 Activity 启动仍需单独满足系统条件 |
| `AppUtils.launchPackage`, `augment.app.App.startActivity` | 宿主直接启动, 没有 PendingIntent / IntentSender | sender options 不适用; 通过实际脚本与系统启动记录核对 |

SOURCE: 生产源集未发现其他 `IntentSender.sendIntent` / `Context.startIntentSender` 发送点. 安装确认回调仍校验 action 与 session ID, 目标 Activity 不导出. 本轮没有更改脚本 API 签名, 不需要更新 d.ts.

## ASM 与诊断边界

PLATFORM_CONFIG: 当前 API 37 镜像的 `dumpsys platform_compat` 显示 `COVER_INTENT_SENDER` (405995292) 与 `ASM_RESTRICTIONS` (230590090) 的 `enableSinceTargetSdk=37`. 后者的 `overridable` 不是 `disabled`. `setAllowCrossUidActivitySwitchFromBelow` 的 API 文档描述的是对任务内下方不同 UID Activity 的约束, 并不是给宿主任意跨应用启动授权. [Activity API](https://developer.android.com/reference/android/app/Activity#setAllowCrossUidActivitySwitchFromBelow(boolean)).

宿主 debug 的 `App.setUpDebugEnvironment` 在 API 36+ 基于已有 VmPolicy 添加 `detectBlockedBackgroundActivityLaunch()` 与 `penaltyLog()`. Release 的 `BuildConfig.DEBUG` 为 false. 保留已有策略, 不启用会因诊断而终止进程的 penalty.

SDK: 本机 API 37 的公开 `IntentSender.sendIntent` options 重载参数顺序是 `(Context, int, Intent, String, Bundle, Executor, OnFinished)`. 在线指南的旧式示例与此不一致. 探针按实际 `android.jar` 编译; `ActivityOptions.fromBundle` 不是可用的公开 API, 探针仅记录公开 `toBundle` 的序列化结果.

## 验证装置

- `ActivityLaunchCompatibilityProbeActivity` 仅在 debug 源集中, 外部启动要求 `android.permission.DUMP`. 它在真实宿主 / inrt UID 下运行, 不使用 instrumentation 或 shell 身份执行待测启动.
- 独立 `org.autojs.sdk37.balfixture` APK 提供固定目标 Activity 与广播回调. Activity token 显式关闭创建方授权, 以便单独观测发送方. Provider 只接受 debuggable 宿主 / inrt 包; 不能请求任意组件或执行任意代码.
- `run_bal_probe.py` 只接受模拟器与 debuggable 应用, 每轮使用独立 case ID 和目录. 保存设备, 权限, compat 配置, Activity / 进程状态, 系统日志和实际目标记录. `sendReturned` 或脚本成功返回不代替实际目标创建.
- 安装探针调用生产 `AndroidPackageArchiveInspector` / `AndroidPackageSessionInstaller`; session 创建结果只代表提交, 最终系统确认与安装结果需另行核对.
- 原始 APK / 系统日志保存在忽略目录 `build/sdk37-p25`; 最终证据只提交与本项有关的记录和哈希.

## 环境记录

- 首个独占只读 AVD 使用 3 GB / 2 vCPU 和镜像默认图形配置, 冷启动及 MainActivity 出现 ANR. 系统记录包含较高 CPU pressure 与 RenderThread 超时, 尚未证明应用根因. 不将该轮计为 BAL 回归结果.
- JDWP 连接后未取得 logpoint 命中, 暂停请求超时. 已停止该调试会话并移除本轮 logpoint, 用户原有 5 个异常断点保持不变. 后续验收脱离调试器.
- 第二实例使用同一镜像的只读副本, 4 GB / 4 vCPU / host GPU. 两次都使用 `-no-snapshot-load -no-snapshot-save -no-window -no-audio`, 不保存快照.
- 第二实例随后从 adb 消失, stderr 中有 gfxstream GL 错误; 原因未完全定位. 后续改用只读 `aj6-ps16k-37-x86_64`, serial `emulator-5568`, 3 GB / 4 vCPU / swiftshader / 关闭 Vulkan, API 37, 16 KB 页大小, 320x640 / 160 dpi. 指纹为 `google/sdk_gphone16k_x86_64/emu64xa16k:17/CE2A.260420.019/15611780:userdebug/dev-keys`.
- 仅在独占 AVD 关闭 TypeScript / Node / OpenCV 插件的预热干扰, 为宿主授予通知权限. BAL 负例中宿主 `SYSTEM_ALERT_WINDOW=deny`, 无已启用无障碍服务. 覆盖权限例外时改为 allow, 每组结束恢复 deny. 为读取系统 ANR 曾临时使用 adb root, 验收前已 unroot 并确认 UID 2000; 待测代码本身始终运行在宿主 UID.
- v1 的两个后台脚本正例未及时完成, 其中一个在脚本回调前就写入 `completed`. v2 改为等待真实脚本回调后再收集目标记录. ASM v1 使用固定 2 秒延迟; v2 改为确认下层 Activity 已 `onStop()` 后再等 12 秒. 原失败记录保留, 不改写为成功.
- 每例停止独立 fixture, 避免先前 Activity 在后台测试时重新露出. `--reuse-process` 只移除宿主 / fixture 的任务并保留宿主热进程. 早期未隔离 fixture 的结果只作辅助; COVER 的最终对照与脚本正例重试使用隔离后的 v2. 初次后台 sender 的目标还曾在观察窗口之后出现, 因此 block 仅表示本次系统拦截记录与即时结果, 不声称该 Activity 此后永远不会创建.
- `android17-release` 的 ASM 源码 URL 三次返回 404. 只记录已读取的官方 API / 行为文档与设备配置, 不用其他分支替代此镜像的运行证据.
