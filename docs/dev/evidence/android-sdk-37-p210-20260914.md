# SDK 37 P2.10: 短信 OTP 可见性与通知监听

日期: 2026-09-14. 会话起点 `373b7ef65`, 工作区干净.
本轮完成普通短信 / 普通 OTP / WebOTP 的即时查询与广播交叉对照.
通知监听的重复投递仍有未定位现象, 三小时后的恢复也未实测, P2.10 不整体关闭.

## 1. 环境和方法

- 独占 `AVD_API_37`, `-port 5590 -read-only -no-snapshot-load -no-snapshot-save -no-window`.
  独立 adb server 5054, serial `emulator-5590`, 使用 `adb emu sms send` 注入虚构短信.
  未操作连接的实体机, 未发送真实短信, 未切换默认短信应用或修改系统时钟.
- 镜像: `google/sdk_gphone16k_x86_64/emu64xa16k:17/CE2A.260420.019/15611780:userdebug/dev-keys`.
  `getconf PAGE_SIZE=16384`, 实际内核页 4096, 不作为真实 16 KB 验证.
- 默认短信应用 `com.google.android.apps.messaging`, 默认 Assistant 角色为 Google 应用,
  系统通知助手为 `com.google.android.as` 的 AiAi 服务. 宿主没有取得这些角色.
- 仅在临时 AVD 内安装本轮 debug 包, 授予宿主 `READ_SMS` / `RECEIVE_SMS` 与通知监听访问.
  脚本检查真实权限状态、默认短信包和监听服务连接. 每组使用独有号码, 只查询该号码.
- 同时保存 shell UID 的入库结果与宿主 UID 的 `content://sms` 查询, 并注册实际
  `android.provider.Telephony.SMS_RECEIVED` 广播和 `events.observeNotification`.
  shell 查询用于确认短信确实入库, 不代表脚本获得了这些内容.
- 每组按顺序注入普通短信、普通 OTP、WebOTP, 间隔 12 秒, 再观察 45 秒.
  成功结束的脚本实际记录约 84-85 秒. 前台窗口、截图、APK / 脚本 SHA-256、
  生效的 compat override、查询时间和回调时间都写入回执.

机器结果见 [P2.10 JSON](android-sdk-37-p210-results-20260914.json).
复跑工具与证据判定测试提交 `71db66ed1`, 入口说明见 [SDK 37 工具](../../../tools/sdk37/README.md#sms-and-notification-listeners).
完整原始数据在忽略目录 `build/sdk37-p210-session-20260914/`, 含失败尝试, 不将失败目录重命名为通过.

## 2. 即时 SMS 矩阵

系统真实分类为普通短信 `contains_otp=0`, 普通 OTP `1`, WebOTP `513`.
最后一条短信使用 `@example.com #736251` 格式, 不是把带数字的任意文本当作 WebOTP.
所有组的系统侧均有三条对应短信, 因而以下不可见结果不能归因于未发送成功.

| target | FILTER_GENERIC_OTP | 普通短信查询 / 广播 | 普通 OTP 查询 / 广播 | WebOTP 查询 / 广播 |
| --- | --- | --- | --- | --- |
| 36 | default / false | 可见 / 收到 | 可见 / 收到 | 不可见 / 未收到 |
| 36 | enable / true | 可见 / 收到 | 不可见 / 未收到 | 不可见 / 未收到 |
| 37 | default / true | 可见 / 收到 | 不可见 / 未收到 | 不可见 / 未收到 |
| 37 | disable / false | 可见 / 收到 | 可见 / 收到 | 不可见 / 未收到 |

这里的 "未收到" 只覆盖记录的观察窗口. 四组共 24 项查询 / 广播可见性比较符合预期,
不等于观察了三个小时, 也不等于验证所有短信读取接口和后台状态.

官方说明区分了 [target 37 的普通 OTP 保护](https://developer.android.com/about/versions/17/behavior-changes-17)
与 [全体应用的 WebOTP 保护](https://developer.android.com/about/versions/17/behavior-changes-all).
对于不在豁免范围的应用, 保护涉及提供者查询过滤与广播延迟; 普通短信不受同样的 OTP 延迟影响.
不能通过在宿主继续请求 `READ_SMS` / `RECEIVE_SMS` 来保证脚本立即取得验证码.

## 3. 当前镜像的提供者代码核对

核对了本机安装的 TelephonyProvider 与 framework 字节码, 不用 AOSP 主分支代替被测系统:

| 文件 | SHA-256 |
| --- | --- |
| `/system/priv-app/TelephonyProvider/TelephonyProvider.apk` | `e6c5cd57fde9f4825bfc4f3b6275528488506235c6c903d53e2b24af68ba28c2` |
| `/system/framework/framework.jar` | `cfd8c422620cf584b5f190d8e5a211b83468a5ffd2bdb5cad1e0e410a22f30d8` |
| `/system/framework/services.jar` | `2485eb8cdea19bd5f95ce9366bd594d7e6c99f3851d2655df041cbdfb3ca4dc0` |

`SmsProvider.query` 使用 `ProviderUtil.getOtpWhereFilter(context, callingPackage, user)`.
该辅助函数检查调用应用的 `FILTER_GENERIC_OTP` (437043173), 并根据分类、时间、
SMS Retriever hash 和已验证域名构造过滤条件. 当普通 OTP 开关关闭时允许普通 OTP,
不会同时放开 WebOTP. `OTP_HIDING_TIME_MS=10800000`, 分类超时常量为 5000 ms.
过期阈值计算还包含分钟取整, 因而不应承诺精确到某一毫秒的恢复时间.
`canReadOtpSms` 委托 `SmsManager.isAppTrustedForSmsOtp`; 本轮没有覆盖各个豁免身份.

这是代码证据与即时行为对照. 真实三小时到期后的查询恢复、延迟广播释放、重启 /
Doze / 后台过程仍需独立长时用例; 没有用修改短信时间戳或修改系统时间代替它们.

## 4. 通知监听: 已证实与保留项

[Android 15 官方说明](https://developer.android.com/about/versions/15/behavior-changes-all)
已经描述了不受信任的通知监听器收到经脱敏的 OTP 通知, 不能将这项规则本身写成 Android 17 新增.

target 36 默认态的正式组, 普通短信正文原样到达 `events.observeNotification`,
随后两次 OTP 通知的 `title` 为空字符串, `text` 和 `EXTRA_TEXT` 为
`Sensitive notification content hidden`, `EXTRA_BIG_TEXT` 为空. 虚构 OTP 未出现在监听回执中.
前一个探索组也有相同结果, 但存在 Launcher ANR 弹窗, 不计入正式通过组.

后续 target 36 enable、target 37 default / disable 组均收到普通通知,
但没有收到预期的两个脱敏更新. target 37 默认态另一次完整重复仍是如此.
随后恢复最终 target 36 包和默认开关、重新授权监听访问后, 完整重复也缺失脱敏更新.
这次脚本持续检查未锁屏并设置保持屏幕常亮, 仍不能消除该现象.
系统 `dumpsys notification --noredact` 则有对应号码的验证码正文与 `mSensitiveContent=true`.
这说明 "系统已发布通知" 与 "脚本收到更新" 必须分别核对; 目前没有证据将缺失归因于
target 37、短信 compat 开关或某个确定的生产代码分支.

早期 runner 只要求普通通知正向对照, 因而一个 target 36 enable 原始回执曾报告成功.
后来补上 OTP 分类 / 负向对照 / 脱敏更新校验后, 归档 JSON 重新验证全部组,
保留 `reportedSuccess` 并另列最终校验错误, 不沿用旧工具的成功标志.
修订后的工具仍会在缺失脱敏回调时返回失败, 不因查询 / 广播通过而放宽通知验收.
四个正式组按完整标准只有一个通过, 三个保留通知回调错误; 两个补充重复组也保留错误.

宿主链路为 `NotificationListenerService.onNotificationPosted` -> `Notification.create`
-> `Events.onNotification` -> 主线程事件. Node 监听器也读取同一个系统回调中的 extras,
但本轮没有运行 Node 的通知 API. 未修改这些生产实现或公开脚本 API.
后续调试通知投递的尝试没有取得可用断点命中, 且有启动 / 调试 ANR 干扰, 不作为根因证据.
