# Android SDK 37 P2.4: Looper / threading

日期: 2026-09-13. 对应 [Roadmap P2.4](../android-sdk-37-roadmap.md#p24-looper--线程-i4).

实现与回归夹具提交: `705cb04ad` (`fix(timers): release scripts after callback cancellation`).

本轮完成宿主的 Looper / 线程适配验证, 并修复验证期间复现的既有定时器退出问题. 正常配置仍为 compileSdk 37 / host targetSdk 36 / inrt targetSdk 29 / minSdk 24. target 37 仅通过 debug 覆盖开关生成测试包. 插件独立进程与打包应用的整体运行时验收仍由 P3 / P5 负责.

## 发现与修复

旧代码用曾经安排过的最大回调时间判断是否还有工作. 清除回调后该时间仍可能位于未来. 当队列已经为空时, IdleHandler 因这个旧时间拒绝退出, 又没有消息在旧时间到达后重新唤醒检查, 脚本便一直存活.

无调试器的两个反例:

1. 原始五秒持续测试已经完成 233 次主线程 / 232 次子线程回调, 子线程已停止, 但脚本在 25 秒等待上限内没有结束 (`baseline.log`, `baseline-logcat.txt`).
2. `cancelled-timers.js` 安排 60 秒后的回调并立即清除, 脚本仍在 20 秒上限内没有结束 (`cancelled-before-fix.log`). 此时设备为 API 37 / target 36 / 三个开关均为默认状态, 所以这是既有逻辑缺陷.

修复位于 [Timer.kt](../../../app/src/main/java/org/autojs/autojs/core/looper/Timer.kt), [Timers.kt](../../../app/src/main/java/org/autojs/autojs/runtime/api/Timers.kt) 与 [TimerThread.kt](../../../app/src/main/java/org/autojs/autojs/core/looper/TimerThread.kt):

- 每次实际投递都有独立登记, 包括不经过 `setTimeout` 等 JS 方法的 `postDelayed` 调用. 正在执行的回调保留到 `finally`, 防止 UI 回调尚未完成时主脚本提前退出.
- 清除定时器时取消对应的排队任务; 在自身回调中清除的 interval 不再重新投递. 清除全部任务同时移除 JS ID, 工作线程退出时清理其 Timer.
- 主脚本检查主线程、UI 和工作线程 Timer 的实际待执行状态. 取消或完成任务时唤醒所属 Looper 和主脚本, 使等待退出的线程能再次检查.
- 保留原有 Timer 构造签名与共享的历史最大时间属性, 退出判断不再依赖该属性. 未读取 MessageQueue 私有字段.

本轮还修正了设备测试前提: instrumentation 会重启应用进程, 系统可能把此前绑定的无障碍服务记为已崩溃. 可复跑工具在测试进程启动后重新绑定已经启用的 AutoJs6 服务, 保留其他服务的启用配置; 测试等待服务实际可用后才执行阻塞查找.

中断探针在默认 target 36 下, 普通线程与 ThreadCompat 均保留原生标记; 单独启用清除开关、组合启用和真实 target 37 下, 两者原生标记均被清除, ThreadCompat 的取消标记仍为 true. 显式 `ThreadCompat.interrupted()` 能清除该标记.

## start 覆写与非 SDK 接口复核

原 Roadmap 的 "8 个 start 文件" 是初始检索估计. 本轮按当前源码复查声明及继承关系, 不把任意名为 start 的方法当作 Thread.start 覆写.

| 类型 / 位置 | 结论 |
| --- | --- |
| `lang.ThreadCompat` | 继承 Thread, 覆写 interrupt / isInterrupted, 未覆写 start |
| `core.looper.TimerThread` | 继承 ThreadCompat, 在 run 内准备 Looper、Timer、Rhino Context, 未覆写 start |
| `runtime.api.Threads.TimerThread` | 继承上述 TimerThread, 覆写 onExit, 未覆写 start; 同时用于 threads.start 与线程池工厂 |
| `FlowWorkerPool.WorkerThread` | 构造阶段设置 daemon, 未覆写 start; lane 内进入 Rhino Context |
| `MainThreadProxy` | 普通包装类, start / interrupt 委托给现有线程, 不是 Thread 子类 |
| `Recorder.AbstractRecorder` / `GlobalActionRecorder` | 录制状态或录制入口, 不是 Thread 子类 |
| `Media.MediaPlayerWrapper` | 覆写 MediaPlayer.start, 不是 Thread.start |
| Lua / Node / AI 会话、插件预加载、输出管道、服务开关及 UI 控制器中的 start | 会话、Runnable 或组合对象的入口, 未发现 Thread.start 覆写 |
| `com.stardust` 兼容代码 | 同类 ThreadCompat / TimerThread / MainThreadProxy 复查; 本轮未修改兼容包 |

未发现宿主生产代码把线程池前置初始化放在 Thread.start 覆写中, 因此没有为此迁移 start 方法. 本轮修复只涉及计时任务登记和退出清理. 插件仓库内部线程实现留给 P5 逐仓复查.

`app/src/main` 的宿主 Looper 实现使用公开 Handler / Looper / MessageQueue.IdleHandler, 未发现对 MessageQueue 私有字段或方法的依赖. `modules` / `plugin-api` 的本仓源码也未发现同类访问. Espresso 已为 3.7.0, 未使用 Robolectric.

`VERIFIED`: Android 17 新 MessageQueue 保留 `mMessages` 字段但其值恒为 null, 不能用它判断队列内容; 官方建议使用公开 API, 并要求相关测试依赖使用支持新实现的版本. 此行为与新 MessageQueue 生效条件相关, 不应泛化成所有旧目标应用始终返回 null. 见 [MessageQueue 官方迁移说明](https://developer.android.com/about/versions/17/changes/messagequeue).

`VERIFIED`: Android 17 上 target 37 应用反射写入 static final 字段会抛出 IllegalAccessException; JNI 写入也可能导致进程崩溃. 这与是否能读取普通字段是不同问题. 见 [target 37 官方行为变更](https://developer.android.com/about/versions/17/behavior-changes-17).

已检查关联文档仓库的 `api/util.md` 与 `api/threads.md`: util.java 现有内容是数组 / 集合转换等工具, 没有修改 MessageQueue 或 static final 的示例; threads 文档也不指导通过覆写工作线程 start 注入初始化. 当前不需要更改公开方法签名或 d.ts. 上述平台限制写入 Roadmap 附录 F, P4 汇总面向脚本用户的升级说明时一并提示.
