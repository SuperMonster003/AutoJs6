## 原生库修复与依据

VERIFIED: Android 17 对 target 37 的 `System.load()` 增加原生库文件只读要求, 可写文件会导致 `UnsatisfiedLinkError`. 本次 API 37 镜像存在 `THROW_ERROR_FOR_WRITABLE_DCL` (463348571), 默认 `enableSinceTargetSdk=37`. [官方目标版本变更](https://developer.android.com/about/versions/17/behavior-changes-17).

SOURCE: 初稿的 "OpenCV / 量化 staging 未设只读" 不准确. 两个 stager 原已调用 `setWritable(false, false)`, 但忽略返回值. 权限设置失败时仍可能返回文件并继续加载.

`OpenCvNativeLibraryStager` / `ImageQuantNativeLibraryStager` 现在:

1. 打开临时文件的写入句柄, 设置文件只读并确认 `setReadOnly()` 成功且 `canWrite()` 为 false, 再使用已经打开的句柄写入.
2. 延续已有 CRC / ELF 校验, sync 与发布流程, 返回最终文件前再次验证只读.
3. 命中校验合格的旧缓存时也执行只读设置与验证, 无需重新提取内容.
4. 任一只读设置或验证失败均使用对应插件既有 `NATIVE_LIBRARY_EXTRACTION_FAILED` 异常. 不增加错误枚举, 字符串资源, JS API 或权限.

每个 stager 增加 4 个测试, 覆盖新文件及旧缓存修复, 新文件设置失败并清理临时文件, 旧缓存修复失败, 设置回调返回成功但文件仍可写. 设备测试另外检查 `Os.stat` 的 user / group / other 写权限位全部关闭. 这里确认的是宿主的 Java 加载链路; 不推断所有 NDK `dlopen` / exec 路径受同一规则约束.

## 旧系统 DEX 修复

DEVICE: API 24 的修复前 APK 可以执行 `runtime.loadDex`, 但随后调用夹具类返回 `TypeError: value is not a function, it is object`. 使用保留的修复前 APK 再次复现并捕获 ART 日志:

```text
--dex-file=/data/user/0/org.autojs.autojs6/cache/classes/safe_sdk37-probe.dex
--oat-location=/data/user/0/org.autojs.autojs6/cache/classes/safe_sdk37-probe.dex
```

SOURCE + DEVICE: `DexClassLoader` 的输入目录与优化目录原来都是 `cacheDir`. API 24 ART 从输入文件名派生 `.dex` 优化产物名, 对原始 `.dex` 输入会使用同一路径, 破坏待加载缓存. 修复为 API 24 / 25 使用私有 `cacheDir/optimized`, 目录创建失败抛 `IOException`; 3 个构造点都使用同一 helper. API 26+ 保持原有目录参数.

VERIFIED: 官方 `DexClassLoader` 文档要求旧系统使用应用私有且可写的优化输出目录, API 26 起该参数不再使用. [DexClassLoader API 参考](https://developer.android.com/reference/dalvik/system/DexClassLoader).

`AndroidClassLoaderRawDexDeviceTest` 嵌入由 `tools/sdk37/fixtures/DexProbe.java` 构建的 DEX. 连续加载两次并反射调用 `value()`, 检查源文件和 staged 文件字节未变, staged 仍只读; API 24 / 25 分支检查优化目录存在. API 24 与 API 37 各 1/1 通过. API 25 本轮没有单独运行设备测试.

保留的前后对照:

- `build/sdk37-p2/dex-jar-api24-baseline-reproduced.log` 与 `-details.log`: 修复前重新安装并复现, 包含上述相同输入 / 输出路径.
- `build/sdk37-p2/dex-jar-api24-final.log` 与 `-details.log`: 修复后 DEX / JAR 各连续两次调用通过, 优化输出位于 `classes/optimized`.
- `build/sdk37-p2/dex-jar-api24-after-baseline-restore.log`: 恢复同一个修复后 APK, 再次验证通过.

## JAR 夹具与既有限制

`tools/sdk37/smoke-dynamic-loading.js` 使用实际 `runtime.loadDex` / `runtime.loadJar` API, 每个输入在同一进程加载两次, 检查返回的 `SDK37_DEX_OK` / `SDK37_JAR_OK`. 仅在所有调用通过后输出 `[SDK37-DCL] PASS: all dynamic loading checks`.

初次 JAR 夹具用 JDK 21 `--release 8` 生成 class major 52. API 37 可正常转换与加载, API 24 则暴露已有编译器限制:

- 本地 D8 路径报 `NoClassDefFoundError: java/nio/file/Paths`.
- Legacy dx 回退报 `ParseException: bad class file magic (cafebabe) or version (0034.0000)`, 随后出现缺少转换输出 JAR 的错误.

日志在 `build/sdk37-p2/compiler-api24-java8-failure.log`. 本轮未升级或改写 D8 / dx; 用本机 JDK 8 `-source 6 -target 6` 生成只引用 `java.lang` 基础类型的 JarProbe (major 50), API 24 / 37 均通过. 因此旧系统结论是 "现有编译器可接受的 JAR 能正常加载", 不代表 Android 7.x 已支持任意 Java 8 JAR. 此限制记录为后续编译器兼容工作.

DEX 夹具仍用 JDK 21 `--release 8` 和 Build Tools 37.0.0 的 D8 `--min-api 24`, 生成 DEX 037. 完整复现命令见 [SDK 37 工具说明](../../../tools/sdk37/README.md#dynamic-loading). 本轮 DEX SHA-256 为 `d1d667f070d0b7f4888930689c6e6a33912c5ca5b50b254e937555fc59670732`; major 50 JAR 为 `9ab5f5cca031ee34a13276a0b3d55ea42867e05d68a488b2e3bccdedc5d3fa09` (JAR 重建时间戳可导致 hash 变化).
