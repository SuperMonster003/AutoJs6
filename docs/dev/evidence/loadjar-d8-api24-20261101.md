# API 24 / 25 的 runtime.loadJar 改走 D8 (2026-11-01)

问题: Rhino class 路线图 P7.2 的设备用例发现 API 24 / 25 的 `runtime.loadJar` 走 legacy dx 1.7.0, 不接受版本 52 (Java 8) 的类文件, 报 `Legacy dx failed (status 1)`; 同一限制在 P5.1 ([apk-size-p5-dexer-20260918.md](apk-size-p5-dexer-20260918.md)) 与 SDK 37 路线图 P2.3 记录过. 维护者拍板 rhino-class Q48 = B: API 24 / 25 的 loadJar 也走 D8.

结论: 把 `desugar_jdk_libs` 换成 `desugar_jdk_libs_nio` 后 D8 在 API 24 / 25 可运行, APK 增加 0.15 MiB. 用户 jar 在所有 API 级别走 D8; API 24 / 25 保留 legacy dx 作 D8 的回退与生成类的首选. 不再需要 Q10 方案 c 的取舍.

## 两条路

| 方案 | API 24 上版本 52 含 lambda 的 jar | APK 体积 | 结论 |
| --- | --- | --- | --- |
| D8 + `desugar_jdk_libs_nio` 2.1.5 | 转换, 加载, 运行都通过 | +159,863 字节 (+0.15 MiB) | 采用 |
| dx 1.16 (build-tools 28, `--min-sdk-version=24`) | `invalid opcode ba`, 失败; `=26` 能转但产物是 `invoke-custom`, API 24 不能执行 | dx.jar 1.04 MB, 与 legacy 1.7.0 (0.99 MB) 相当 | 不采用: 只能解决不含 lambda 的类 |

dx 1.16 在桌面 JVM 上验证, 未上设备. 体积是 universal debug 包, 同一克隆里只改依赖的两次干净打包: 48,978,009 -> 49,137,872; dex 原始大小 88,374,272 -> 88,571,724. 增量打包的 APK 含空洞 (曾到 51.5 MB), 比较体积要看干净打包或条目压缩大小之和. 库 jar 在两个变体里是同一个文件, 差别只在 L8 的配置.

## 转换路径

| 入口 | API 26+ | API 24 / 25 |
| --- | --- | --- |
| `runtime.loadJar`, `loadAar` (`AndroidClassLoader.loadJarLocally`) | D8, 失败后对 zip4j 重打包副本再试 D8 (不变) | 同左, 重打包副本上 D8 再失败时回退 legacy dx |
| 脚本引擎 Java 桥接的 `loadJar` (`RuntimeJavaSession`) | D8 (不变) | D8, 失败回退 legacy dx (`ClassFileDexer.convertToDexJar`) |
| `defineClass`, `JavaAdapter`, 桥接生成的子类 | D8 (不变) | legacy dx 优先, 失败转 D8 (`convertGeneratedToDexJar`) |
| 有序 classpath (`jarToDexR8(plan)`) | D8 (不变) | D8, 去掉 `D8.main` 分支: 它在失败时 `System.exit`, 现在 D8 真能运行, 这个分支成了结束进程的风险 |

保留 legacy dx 的理由见下节: 生成类的首次开销. 两种转换都失败时报 D8 的错误, legacy dx 的错误作为 suppressed 附上; 坏 jar 不再显示误导的 `Legacy dx failed`.

配置要点 (`desugar.json` 2.1.5 nio): `java.nio.file` 的异常类是 `maintain_type`, 不改名, 宿主 `catch (FileAlreadyExistsException)` 等照常生效; `Path`, `Files` 等改写到 `j$.nio.file`, API 26+ 经包装转到平台实现.

## 耗时

都是 debug 包. API 24 AVD 上读不到 PCY 与 cpuset. 本机负载对绝对值影响很大, 应看同一时段的比值.

API 24 AVD (google_apis x86), 新进程内连续 6 次转换, 单位 ms:

| 时段 | 转换 | 首次 | 第 2-6 次 |
| --- | --- | --- | --- |
| 本机负载较低 | D8, 版本 52 | 1381 / 1745 / 1889 | 97-524 |
| 本机负载较低 | D8, 版本 51 | 1924 / 1563 / 1271 | 57-167 |
| 本机负载较低 | legacy dx, 版本 51 | 359 / 323 / 234 | 29-166 |
| 本机 CPU 100% | D8, 版本 52 | 3446 / 4513 / 5075 / 6246 | 155-1310 |
| 本机 CPU 100% | legacy dx, 版本 51 | 586 / 571 / 561 / 878 | 31-382 |

D8 的进程内首次运行约为 legacy dx 的 5-6 倍, 之后约 2-3 倍. `runtime.loadJar` 一个进程只付一次这笔开销, 所以接受; 适配器类在脚本里更常见, API 24 / 25 仍走 legacy dx.

继承 Java 类的首次构造 (`firstConstructionCost`, 120 轮, 取最后 30 轮), API 24 AVD, 同一时段交替运行, 单位 ms:

| 构建 | 第 1 轮 | 暖机后中位数 | 最小值 |
| --- | ---: | ---: | ---: |
| 改动前 | 687 | 264 | 65 |
| 改动后 | 878 | 169 | 77 |
| 改动前 | 1509 | 254 | 151 |
| 改动后 | 1156 | 211 | 110 |

XQ-AT72 (API 31, PCY fg, 少数采样为 bg) 上 D8 转版本 52 的 jar, 新进程内首次: 改动前 647 / 664 / 761 / 869 ms, 改动后 713 / 861 / 886 / 751 ms; 第 2-6 次两边都是 176-292 ms. `firstConstructionCost` 暖机后中位数 95.64 ms, P7 记录为 95.14 ms. API 26+ 没有可见变化.

## 脱糖文件系统的差异

- API 24 / 25 上 `Files.move` 移动不存在的源文件时不抛异常, API 35 抛 `NoSuchFileException`. 宿主的 `Files.move` 在 API 26 以下都有门控 (`EditorFileService`, `R8CompilerArtifactExporter`, `NodeBridgeFileScope`), 不受影响; 新代码若在这两个 API 级别直接用, 要先判断源文件存在.
- `JavaNioDesugarDeviceTest` 覆盖宿主用到的调用: 读写, 复制, 删除, 三种 `move`, 异常类型, 路径比较, 符号链接. JVM 单测用的是真正的 `java.nio.file`, 覆盖不到这一层.

## 未覆盖

没有 API 24 / 25 的真机, 这两个 API 级别只在 AVD 上验证. 耗时是 debug 包, x86 AVD 的绝对值不代表旧手机.
