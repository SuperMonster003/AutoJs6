## 1. 小组件路径丢失的修复

生产 `ScriptWidgets.removeAllNotIn()` 使用 `[a-zA-Z]+_([0-9])+` 解析偏好键. 量词位于捕获组外, 多位 ID 只返回最后一位. 修复前, 实际注册的 widget 38 / 39 经生产 `ScriptWidget.onUpdate()` 批量更新后, `path_38` / `path_39` 和对应 `rc_*` 都被清理. 从已安装 APK 读取其实际 Pattern 对象得到捕获值 `8` / `9`, 与真实 SharedPreferences 丢失结果一致.

修复提交 `6ab016582` 改为 `[a-zA-Z]+_([0-9]+)`, 保留完整 ID. 测试使用系统 AppWidgetHost 分配多个 ID, 将两个多位 ID 绑定到真实 ScriptWidget provider, 然后验证:

1. 批量更新后两组路径和不同的 PendingIntent requestCode 均保留, 过期映射被清理.
2. 实际 AppWidgetHostView 的标签等于脚本文件名.
3. 点击生产 RemoteViews 中的 PendingIntent, 实际 Rhino 脚本写入 `first` 标记.
4. 更换脚本、更新同一 widget 并再次点击, 实际写入 `second` 标记.

[实际宿主视图截图](android-sdk-37-p28-p29-screens-20260913/widgets37-final.png) 保存更新后的脚本标签与生产资源图标; 点击成功由独立文件标记断言, 不能只凭截图判断.

这不是 Android 17 独有的回归, 而是在 P2.9 验证中发现的已有缺陷. 修复没有修改公开脚本 API 或小组件配置格式. 已补充 6.8.0 的十种语言 fix 日志, 并运行 Markdown 生成脚本.

调试过程按 `ij-debugger` 技能尝试: 建立 Remote JVM 会话和不暂停的日志断点, 但没有命中事件, PAUSE / STOP 请求超时. 没有取得 debugger 变量证据. 随后采用实际 APK Pattern 对象和系统小组件 / 偏好结果作对照. 临时 run configuration、端口转发和本轮断点均已清理, 既有五个用户断点未改动.

## 2. 小组件内存限制: 公告与镜像差异

[官方 Android 17 说明](https://developer.android.com/about/versions/17/behavior-changes-17#memory-limit-widget) 称 target >= 37 会将 RemoteViews 的 Bitmap 和 Icon 合并计入 `1.5 * screen width * screen height * 4` 上限. 当前 `CE2A.260420.019` 镜像的实际 `AppWidgetServiceImpl.ensureWidgetViewsMemoryLimitLocked()` 则只在 **target > 37** 时将 Icon 加入抛错判断; target <= 37 超出合计上限时输出警告. 设备字节码明确使用 `if-le ... 37` 分支, 日志为 `This will throw an exception for targetSdk > 37`.

本机屏幕 1080x2424, 服务上限 15,707,520 bytes. 夹具创建 1080x3879 的 ARGB_8888 图, 分配 16,757,280 bytes:

| 输入 | target 36 | target 37 | 结论 |
| --- | --- | --- | --- |
| 生产 ScriptWidget, 资源图标和文本 | 注册、更新、点击通过 | 同左 | 正常小组件回归通过 |
| `setImageViewIcon(Icon.createWithBitmap(...))` | 接受, 服务警告 | 接受, 同一警告 | 此镜像不能证明公告所述 target 37 Icon 拒绝分支 |
| `setImageViewBitmap(...)` | 超限 IllegalArgumentException | 同左 | 原有 Bitmap 限制的负例有效 |

首次按公告预期 target 37 Icon 被拒绝的测试确实失败, 保留在机器结果, 没有将失败改写为平台已满足公告. 复跑工具要求显式传入 `--expect-widget-icon-rejected`, 并在接受分支核验实际系统警告. 这里不升级项目到 target 38, 也不通过修改平台策略制造通过结果. 后续需在更新的 API 37 镜像 / 真机复核差异.

## 3. 通知自定义视图检查

从设备的 SystemUIGoogle APK 定位到 `NotificationRowContentBinderImpl.Companion.validateView()` 与 `NotificationCustomContentMemoryVerifier`:

- 先判断通知是否包含自定义视图, 再遍历渲染后的 View 层级, 汇总 ImageView drawable 内存. BitmapDrawable 使用 allocation byte count, AdaptiveIconDrawable 递归计算, 其它 drawable 使用固有尺寸估计.
- 使用发送通知应用 UID 的 `CHECK_SIZE_OF_INFLATED_CUSTOM_VIEWS` (270553691), 不是 SystemUI 自身 target 的替代值.
- 当前镜像资源 `config_notificationWarnRemoteViewSizeBytes=2000000`, `config_notificationStripRemoteViewSizeBytes=5000000`. 这些是此镜像的资源值, 不是可硬编码到所有设备的 API 常量.
- 超过较大阈值且 compat 开启时, SystemUI 输出包含本次通知 ID 的拒绝日志, 抛出内部 `CustomViewMemorySizeExceededException`. 应用侧 `notice()` 可以正常返回, NotificationManager 的记录仍为 active, 通知栏仍可显示标题. 因此不以 active 状态证明自定义内容成功显示, 也不将该行为描述为应用同步抛错或通知记录必然消失.

夹具用同一 256x256 ARGB_8888 Bitmap 构造 21 个 ImageView, 原始图像合计 5,505,024 bytes. SystemUI 实测合计为 5,591,460 bytes, 加上系统装饰后超过 5,000,000 阈值. 关闭开关时输出将来拒绝的警告; 开启时记录拒绝. 日志必须匹配本轮通知 ID, 不能借用之前用例的输出.

普通 `notice` / BigText、真实 AppForegroundService 通知、小型自定义 content / bigContent 与超限负例分别产生回执. 前台服务通知可能延迟显示, 夹具等待实际通知出现后再检查 FLAG_FOREGROUND_SERVICE 和 channel, 不把服务启动返回当作通知通过. 通知栏层级、截图和清理确认均保留.

target 37 的 [开关关闭截图](android-sdk-37-p28-p29-screens-20260913/notifications37-disabled-final.png) 中超限自定义图片仍可见; [默认开启截图](android-sdk-37-p28-p29-screens-20260913/notifications37-final.png) 中该内容被剥离, 保留标准标题. 两者的小型自定义内容、普通通知与真实前台服务通知均可见, 与按各自通知 ID 匹配的日志共同构成证据.

target 36 默认状态出现相同内存警告; [显式开启后](android-sdk-37-p28-p29-screens-20260913/notifications36-enabled-final.png) 同样剥离超限自定义内容. 因而此通知规则已验证实际 compat 门控, 并非仅观察到两个不同 target 包的差异.

## 4. 生产通知构建点与脚本用法

源码检查的当前构建点包括 `ForegroundServiceUtils`、`PythonLongRunningForegroundService`、`NotificationUtils`、`NodeAudioRecorder`、`PackageInstallStatusCoordinator`、`NodeBridgeProtocol` 和 `PythonHostCapabilityBroker`. 这些内建通知使用标准模板, 没有设置自定义 content / bigContent / heads-up RemoteViews. 监听器的 Notification 包装类复制这些字段属于接收路径. 当前 CrashHandler 打开 CrashReportActivity, 没有独立的崩溃通知构建入口, 原 Roadmap 的这一假设已纠正.

公开 `notice(builder, options)` 确实接受 `NotificationCompat.Builder`, 因而脚本可以使用自定义 RemoteViews. 本轮不改变 builder 或通知的公开契约; 使用说明如下:

- 优先使用普通 `notice({title, content, bigContent})` 或标准样式. 自定义视图只有在系统实际渲染时才能完整计算其图片占用, 应用侧 `notify()` 成功不能保证自定义内容显示.
- 自定义图片先缩放到实际显示尺寸. 多个 ImageView 即使共享同一 Bitmap, 仍可能被此镜像逐个累计; URI / resource 图像也需要考虑解码后的大小, 不能只检查压缩文件大小.
- 使用 [官方自定义通知指南](https://developer.android.com/develop/ui/views/notifications/custom-notification) 的装饰样式和布局建议, 同时检查折叠、展开、heads-up、横屏和不同显示密度. 该指南中的布局高度约束与本轮图片内存限制是两类检查.
- 为自定义通知提供可读的标准 title / content, 并保留可用的普通模板方案. 不把 try/catch 包住 `notice()` 当作捕获所有 SystemUI 渲染失败的办法, 不依赖关闭兼容开关作为生产解决方案.

## 5. 验证边界与后续

本轮完成真实小组件功能回归、内存控制对照、标准 / 自定义通知代表路径及生产构建点审计. 完整有效矩阵及每次执行版本见机器结果. 未重跑 Python 长任务、Node 录音、Python 录音等每一种业务触发链路的通知生命周期; 它们的完整业务回归继续保留. 实际 launcher 的添加 / 重建 / 删除、OEM SystemUI / 方向 / 密度变化和真实 16 KB 内核验收仍需对应设备.
