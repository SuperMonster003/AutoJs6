# P6.2 ColorOS 抽样 (OnePlus OPD2413, API 35)

日期: 2026-11-02. 会话: api-cov-p6-2-coloros. 设备: OnePlus OPD2413, serial `63751f63`, ColorOS V15.0.1 (`OPD2413_15.0.1.801(CN01)`), Android 15 / API 35, arm64-v8a.

## 抽样清单 (执行前写定)

方法: `tools/api-coverage/device_p6_2_coloros.py`. 本卡不重复 P3 / P4 的用例表 (P3.5 / P4.5 收口 A 在本机跑过 78 项四形态, P4.2b 跑过 Bun 拒绝轮), 只看 ColorOS 与其他设备不同的地方: 系统侧授权的给予与收回, 插件进程不在时的绑定, 后台冻结. 每个用例在 Rhino, Node main, Node Worker, Bun main, Bun Worker 五种形态各跑一次, 与期望值或同轮 Rhino 值比对.

### 授权类入口 (auth 阶段)

| 授权类 | 系统侧授权 | Node 能力 / Bun 授权 | 入口 | 为什么在 ColorOS 值得测 |
|---|---|---|---|---|
| engines.exec | 无 | `engines.exec` / `engines.exec` | `engines.execScript` (子引擎须真的打出标记) | 插件进程里的脚本让宿主起引擎, 宿主此时在后台, 可能已被冻结 |
| 共享存储 | 所有文件访问 (按插件 UID) | `files.write` / `files.control` | `files.write`, `fs.writeFileSync` | 插件进程没有应用内入口 (Q228), ColorOS 权限页与 AOSP 不同; Bun 清单未声明该权限, `fs` 预期 EACCES |
| 无障碍 | 无障碍服务 | `accessibility` + `.gesture` / 同名授权 | `auto.state`, `automator.press` | ColorOS 会停掉或解绑后台应用的服务, 手势要经绑定中的服务 |
| 悬浮窗 | 显示在其他应用上层 | `ui.overlay` / `floaty.control` | `floaty.checkPermission`, `floaty.window`, `floaty.rawWindow` | 该权限同时决定宿主在后台时能否唤醒插件 |
| 通知 | POST_NOTIFICATIONS, 渠道 | `notifications` / `notifications.post` | `notice.isEnabled`, `notice.channel.create`, `notice.notify` (核对 `dumpsys notification`) | ColorOS 有自己的通知管理 |
| 通知监听 | 通知使用权 | `events.notification` / 同名授权 | `events.observeNotification` | 监听服务绑定在后台可能被系统断开 |
| 前台服务 | FGS mediaPlayback | `media.playback` / `media.control` | `media.playMusic` (静音 WAV, 核对 `isForeground`) | 宿主在后台启动前台服务, 且要确实在前台运行 |
| keepAwake | WAKE_LOCK | `device.power` / 同名授权 | `device.keepAwake` (核对 `dumpsys power`) | ColorOS 电源管理可能剥夺后台应用的唤醒锁 |
| 电池优化 | 忽略电池优化 | `device.power` / 同名授权 | `powerManager.isIgnoringBatteryOptimizations` | 脚本读到的值要与系统名单一致 |
| 后台启动 | 后台弹出界面 | `app.launch` / `app.control` | `device.roms.isBackgroundStartGranted`, `app.launchPackage` | 宿主在后台时启动 Activity |
| 剪贴板 | 后台读剪贴板限制 | `clipboard` / `clipboard.control` | `setClip` + `getClip` | 后台应用读剪贴板受限 |
| Shizuku | Shizuku 授权 | `shell.shizuku` / 同名授权 | `shizuku.state`, 服务在运行时加 `shizuku.execCommand` | 宿主拿 Shizuku binder, 服务未运行时要如实报告 |
| 安装器 | 安装未知应用 | `installer` / `installer.control` | `installer.isAvailable` (只查询) | 真实安装有确认页, 不在自动范围 |

### 授权收回 (denied 阶段)

收回后入口要给出错误或 false, 不能挂起: 悬浮窗 (`appops` deny), Node 所有文件访问 (`appops --uid` deny), 无障碍 (写回原列表), 通知 (`pm revoke`). 全部由 `prepare` 记录, 结束写回.

### provider 绑定与重绑 (rebind / midrun / instrument)

| 场景 | 做法 | 为什么在 ColorOS 值得测 |
|---|---|---|
| 绑定被拒即唤醒 | 脚本前 `am force-stop` 六类 provider (Batch Rename, 3-Maple Image, 3-Hanzi CC, 3-Macaw Speech, OCR, 工具插件), 五形态各调一次, 统计 `PluginAutoWake` 的 `woke` 行 | ColorOS 在进程不在时一律拒绝绑定, 新桥接都要经 PluginAutoWake |
| 运行时自身被唤醒 | 同时停 Node / Bun 插件, 记录首个结果耗时 | 运行时进程走同一条路 |
| 前台 / 后台 / 无悬浮窗 | `--variant background | foreground | no-overlay` | 唤醒要宿主在前台或有悬浮窗权限, 第三种是预期的限制, 要看错误是否清楚 |
| provider 在脚本中途被杀 | 同一脚本两次调用之间 `am force-stop` | 宿主要在同一执行里重绑 |
| 运行时在脚本中途被杀 | Node / Bun 各一次, 核对无残留引擎, 下一脚本能跑 | 进程死亡不能让执行挂起 |
| 宿主在脚本中途被杀 | Node / Bun 各一次, 核对运行时进程退出 | 不能留下无主执行 |
| 插件中心列表不唤醒, 用户请求唤醒未启用插件, 退避 | `PluginAutoWakeDeviceTest` 五项 | 既有设备测试, 覆盖 `Off` / `UserRequest` |
| MCP 重绑用 Rebind 模式 | MCP 仓库 `tools/evidence/listener_rebind.py` | 抽屉监听器由维护者打开 |

### 前台服务与后台冻结 (background / capture)

| 场景 | 做法 | 为什么在 ColorOS 值得测 |
|---|---|---|
| 宿主在后台的脚本 | 每 3 s 调一次宿主, 跑 60 s, 记录最长间隔, 超过 9 s 记冻结; 宿主前台服务关 / 开 × 亮屏 / 灭屏 | 既有记录是长跑时宿主与插件进程被冻结 |
| MediaProjection | 五形态各一次, 维护者点系统对话框, 核对 `ScreenCapturerForegroundService` 在前台 | 同意后要及时进前台服务, 自动点击用例不适用 ColorOS 对话框 |

### 执行中的调整

清单写定后追加或改动的项, 都写明原因:

- `a11y` 阶段: 无障碍在宿主被杀后没有回来, 另测三种结束方式, 并用 AVD_API_33 对照.
- `rebind --variant background-late / no-overlay-late`: 脚本开始 25 s 后才调用 provider, 这时宿主自己的启动宽限已过.
- `background --a11y on|off` 与 `freeze`: 绑定中的无障碍或通知监听都让宿主不进 cached 状态, 所以 "off" 两者都关. 宿主要先 `am force-stop`, 否则刚在前台过的宿主不会被冻结, 看起来像通过.
- `prompt` 阶段: Q228 (b) 在本卡进行中落地 (宿主 776f50a8a / 74b6e8120 / dd4d01c73, Bun d8eb960), 候选包换到含它的 HEAD 后加测. Bun 已声明所有文件访问, 上表 "`fs` 预期 EACCES" 只适用于第一批; 分区存储下的实际错误码是 EPERM.
- `concurrent` 阶段: 量 Bun 并发 `getAccess` 超时的复现率.
- 宿主在脚本中途被杀: 上表写的 "核对运行时进程退出" 不是正确的判据. 运行时进程本来就空闲保留, 改为核对脚本是否结束, 下一脚本能否运行.

## 结论

- 授权类 13 类 21 项, 五形态全部通过 (`shizuku.exec` 因服务未运行跳过); 收回授权 7 项全部给出错误或 false, 没有挂起.
- ColorOS 的 provider 绑定与重绑全部工作: 六类 provider 五形态 34 / 34, 宿主在前台, 在后台, 无悬浮窗权限 (启动宽限内) 三种情况相同; 脚本中途杀 provider, 杀运行时, 杀宿主都有正确结果; `PluginAutoWakeDeviceTest` 5 项通过, MCP 抽屉监听器重绑 4 项检查通过.
- 只有 1 条是 ColorOS 限制: 宿主进程崩溃或被系统杀掉后, 无障碍服务不自动重绑 (AOSP 14 s 内重绑). 登记 Q240, 推荐不加矩阵标注, 已写进文档.
- 后台冻结不是 ColorOS 限制: AOSP API 35 同样在约 12 s 后停住. 宿主没有自己的 Activity, 也没有前台服务和绑定中的系统服务时, Rhino / Node 停到宿主回前台, Bun 场景的宿主被系统杀掉. 前台服务开启时 10 行全部不停. 登记 Q241.
- 过程中发现 1 个真缺陷, 已修并复测: 没有 su 的设备上两个首次 root 检查同时进行时丢应答, Bun 并发 `getAccess` 从 10 轮 8 次超时降到 0 次 (宿主 803bf1e65, 与 ColorOS 无关).
- Q228 (b) 的提示在 ColorOS 上走通: 拒绝时提示一次, 授权入口进入系统页 `Settings$AppManageExternalStorageActivity`, 授权后写入成功且不再提示; 查询其他包的 appop 在 ColorOS 上可用.

## 失败项逐条判定

| 项 | 现象 | 是否 ColorOS 限制 | 处理 |
|---|---|---|---|
| 无障碍崩溃后不重绑 | `am crash` / `pm revoke` 后不自动重绑, 重写设置才恢复 | **是**. AOSP 14 s 内重绑; `force-stop` 两边都不重绑 | Q240, 写进文档, 矩阵不加标注 |
| 后台脚本停住 | 宿主无 Activity, 无前台服务, 无绑定时约 12 s 停住 | 否. AOSP API 35 相同, 是 Android 14 起的 cached 进程冻结 | Q241, 写进文档 |
| Bun 场景宿主被杀 | 同上状态下 `Kill app due to repeated failure to freeze binder` | 否. 这是平台冻结 binder 失败时的处理; AOSP 上未跑 Bun, 配置 `freeze_binder_enabled` 相同 | Q241 |
